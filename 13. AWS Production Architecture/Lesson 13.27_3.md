# S3 Versioning, Object Lock, Replication & Data Recovery

We have solved two S3 questions:

```text
Part 1
"What is S3?"

Part 2
"Who is allowed to access S3?"
```

Now we solve:

> **“What happens when an authorized person or application accidentally overwrites or deletes production data?”**

This moves us into **data protection**.

```text
                        S3 DATA
                           │
              ┌────────────┼────────────┐
              │            │            │
              ▼            ▼            ▼
           Versioning   Object Lock   Replication
              │            │            │
        recover old      prevent      maintain
         versions        deletion      copies
              │            │            │
              └────────────┼────────────┘
                           ▼
                      DATA PROTECTION
                           │
                    Lifecycle / Backup
```

---

# 1. The Problem Without Versioning

Suppose your bucket contains:

```text
prod-assets
└── application/config.json
```

Current data:

```json
{
  "database": "prod-db",
  "environment": "production"
}
```

Then someone accidentally uploads another file using the **same key**:

```bash
aws s3 cp bad-config.json \
  s3://prod-assets/application/config.json
```

Without Versioning:

```text
config.json V1
      │
      │ overwrite
      ▼
config.json V2

V1 effectively gone
```

Similarly:

```bash
aws s3 rm \
  s3://prod-assets/application/config.json
```

can permanently remove the object in an unversioned bucket.

This is one of the major reasons Versioning exists.

---

# 2. S3 Versioning

When Versioning is enabled, S3 preserves multiple variants of the **same object key**.

Instead of:

```text
config.json
```

think:

```text
config.json
│
├── Version A
├── Version B
├── Version C
└── Version D ← current
```

Each new PUT of the same key creates another object version instead of overwriting the old version. ([AWS Documentation][1])

---

# 3. Version ID

Each new version gets an S3-generated:

```text
VersionId
```

Conceptually:

```text
Bucket:
prod-data

Key:
config.json

VersionId:
A1BCD...

             ↓

one exact object version
```

Therefore:

```text
Bucket
+
Key
+
VersionId
```

uniquely identifies a particular version.

Version IDs are generated by S3 and treated as opaque identifiers—you shouldn't try to derive meaning from their contents. ([AWS Documentation][2])

---

# 4. Example Version History

Imagine:

```text
10:00
config.json
Version A

11:00
config.json
Version B

12:00
config.json
Version C
```

Normal:

```bash
aws s3 cp \
  s3://prod-data/config.json \
  .
```

returns:

```text
Version C
```

because C is current.

But earlier versions remain available:

```text
A
B
C ← current
```

# 5. Enable Versioning

For our lab:

```bash
export AWS_REGION="ap-south-1"

ACCOUNT_ID=$(aws sts get-caller-identity \
  --query Account \
  --output text)

BUCKET="lesson27-versioning-${ACCOUNT_ID}-$(date +%s)"
```

Create:

```bash
aws s3api create-bucket \
  --bucket "$BUCKET" \
  --region "$AWS_REGION" \
  --create-bucket-configuration \
    LocationConstraint="$AWS_REGION"
```

Enable versioning:

```bash
aws s3api put-bucket-versioning \
  --bucket "$BUCKET" \
  --versioning-configuration Status=Enabled
```

Verify:

```bash
aws s3api get-bucket-versioning \
  --bucket "$BUCKET"
```

Expected:

```json
{
  "Status": "Enabled"
}
```

Versioning is disabled by default on an ordinary newly created bucket until you enable it. ([AWS Documentation][3])

---

# 6. Upload Version 1

```bash
echo "version-1" > config.txt
```

Upload:

```bash
aws s3api put-object \
  --bucket "$BUCKET" \
  --key app/config.txt \
  --body config.txt
```

The response should include a:

```text
VersionId
```

Now:

```bash
echo "version-2" > config.txt
```

Upload again:

```bash
aws s3api put-object \
  --bucket "$BUCKET" \
  --key app/config.txt \
  --body config.txt
```

Then:

```bash
echo "version-3" > config.txt
```

Upload again.

Our logical S3 history is now:

```text
app/config.txt
│
├── V1 = version-1
├── V2 = version-2
└── V3 = version-3   ← CURRENT
```

Every overwrite creates a new version rather than replacing the older versions. ([AWS Documentation][2])

---

# 7. List Versions

Run:

```bash
aws s3api list-object-versions \
  --bucket "$BUCKET" \
  --prefix app/config.txt
```

Useful query:

```bash
aws s3api list-object-versions \
  --bucket "$BUCKET" \
  --prefix app/config.txt \
  --query 'Versions[].{
      VersionId:VersionId,
      Latest:IsLatest,
      LastModified:LastModified,
      Size:Size
  }' \
  --output table
```

You'll see something conceptually like:

```text
Version       Latest
---------------------
v3            true
v2            false
v1            false
```

# 8. Recover From Accidental Overwrite

Suppose V3 is bad.

Current:

```text
V1 good
V2 good
V3 BAD ← current
```

We want V2.

There are two common strategies.

### Strategy A — Retrieve the old version

```bash
aws s3api get-object \
  --bucket "$BUCKET" \
  --key app/config.txt \
  --version-id "$VERSION_2" \
  restored-config.txt
```

You now have the old data.

### Strategy B — Make old content current again

You can copy the older version back onto the same key, creating a **new current version** whose content matches the historical version. AWS documents copying previous versions as a recovery technique. ([AWS Documentation][4])

Conceptually:

```text
V1
V2 ← wanted
V3 bad

copy V2

↓

V1
V2
V3 bad
V4 = content from V2 ← current
```

Notice we didn't destroy history.

---

# 9. What Happens When You DELETE?

This is where S3 Versioning becomes really interesting.

Suppose:

```text
document.pdf

V1
V2
V3 ← current
```

Run:

```bash
aws s3 rm \
  s3://$BUCKET/document.pdf
```

without specifying a version ID.

S3 does **not normally erase V3**.

Instead it creates:

# Delete Marker

```text
document.pdf

V1
V2
V3
DELETE MARKER ← current
```

The delete marker becomes the current version, so ordinary GET/LIST behavior makes the object appear deleted while the old versions remain. ([AWS Documentation][1])

---

# 10. Delete Marker Mental Model

Think of a delete marker as:

```text
"Hide this object from normal current-version access."
```

not:

```text
"Destroy every byte permanently."
```

Example:

```text
Version History

V1
 │
V2
 │
V3
 │
DELETE MARKER ← current
```

Now:

```bash
aws s3 cp \
  s3://bucket/document.pdf \
  .
```

behaves as if:

```text
object doesn't exist
```

because the delete marker is current.

But V1/V2/V3 are still there.

---

# 11. How to Undelete the Object

List versions:

```bash
aws s3api list-object-versions \
  --bucket "$BUCKET" \
  --prefix document.pdf
```

You'll see something like:

```text
Versions
--------
V3
V2
V1


DeleteMarkers
-------------
DM1 ← latest
```

To undelete:

```bash
aws s3api delete-object \
  --bucket "$BUCKET" \
  --key document.pdf \
  --version-id "$DELETE_MARKER_VERSION_ID"
```

After removing the current delete marker:

```text
V3
```

becomes current again.

AWS explicitly documents deleting the delete marker as the standard undelete mechanism. ([AWS Documentation][5])

---

# 12. Soft Delete vs Hard Delete

You must distinguish these.

### Normal DELETE without version ID

```bash
DELETE object
```

in a versioned bucket:

```text
creates delete marker
```

Think:

```text
SOFT DELETE
```

### DELETE with specific version ID

```bash
DELETE object?versionId=abc123
```

means:

```text
permanently remove that version
```

Think:

```text
HARD DELETE
```

AWS's DeleteObject API documentation states that specifying a version ID permanently deletes that version. ([AWS Documentation][6])

### Never forget

```text
Versioned bucket:

DELETE key
=
delete marker


DELETE key + versionId
=
permanent version deletion
```

---

# 13. Versioning Is Protection — But Not Absolute Immutability

This distinction is critical.

Versioning protects against:

```text
accidental overwrite
simple accidental delete
application replacing object
```

But a sufficiently privileged principal could execute:

```text
DeleteObjectVersion
```

and permanently delete historical versions.

Therefore:

```text
Versioning
≠
WORM protection
```

This is where Object Lock becomes important.

---

# 14. Versioning Storage Cost

Suppose your object:

```text
database-backup.tar.gz
=
100 GB
```

You upload five different versions.

Conceptually your storage usage can become roughly:

```text
V1 100 GB
V2 100 GB
V3 100 GB
V4 100 GB
V5 100 GB

≈ 500 GB
```

depending on object sizes.

S3 doesn't perform EBS-snapshot-style block-level incremental version storage for ordinary versioned objects.

Each object version is billable storage.

Therefore Versioning should usually be combined with:

```text
Lifecycle Management
```

to control old-version cost.

# 15. Current vs Noncurrent Versions

For a key:

```text
report.pdf

V1
V2
V3
V4
```

where:

```text
V4 = current
```

then:

```text
V1
V2
V3
```

are:

# Noncurrent Versions

Lifecycle rules can independently manage:

```text
current versions
```

and:

```text
noncurrent versions
```

AWS specifically recommends adding noncurrent-version lifecycle actions when Versioning is enabled if you want older versions eventually deleted or transitioned. ([AWS Documentation][1])

# 16. Lifecycle Example

Production policy:

```text
Current object
    │
    │ 30 days
    ▼
STANDARD_IA
    │
    │ 90 days
    ▼
Glacier

Noncurrent version
    │
    │ retain 30 days
    ▼
DELETE
```

This can protect recent mistakes while preventing thousands of obsolete versions from accumulating forever.

Terraform conceptually:

```hcl
noncurrent_version_expiration {
  noncurrent_days = 30
}
```

We'll cover complete Lifecycle engineering in the next S3 part.

# 17. Suspending Versioning

Once Versioning has been enabled, you normally don't return the bucket to:

```text
never versioned
```

You can change its state to:

```text
Suspended
```

AWS allows enabled Versioning to be suspended; existing versions remain and future requests use suspended-version behavior. ([AWS Documentation][1])

Mental model:

```text
Never versioned
      ↓
Enabled
      ↓
Suspended
```

Not:

```text
Enabled
→ erase version history
```

Suspension doesn't clean up historical versions.

---

# 18. Objects That Existed Before Versioning

Suppose your bucket already had:

```text
old-object.txt
```

before Versioning was enabled.

That existing object has:

```text
VersionId = null
```

Enabling Versioning does not rewrite all existing objects. Future modifications create normal version IDs. ([AWS Documentation][1])

Conceptually:

```text
Before Versioning

object
VersionId=null


Enable Versioning


overwrite object
     ↓

V2 = generated VersionId
V1 = null
```

That's a useful troubleshooting detail.

---

# 19. MFA Delete

Now another protection mechanism:

# MFA Delete

MFA Delete adds MFA requirements around especially sensitive versioning operations.

When enabled, MFA is required to:

```text
permanently delete object versions

change bucket versioning state
```

AWS documents that only the **AWS account root user** can enable or disable MFA Delete and permanently delete protected versions under this mechanism, using MFA authentication. ([AWS Documentation][7])

---

# 20. MFA Delete Is Not Normal IAM MFA

Don't confuse:

```text
IAM policy requiring MFA
```

with:

```text
S3 MFA Delete
```

They are different mechanisms.

MFA Delete is tied specifically to:

```text
S3 Versioning configuration
+
permanent version deletion
```

It also can't be enabled from the standard S3 Management Console; AWS documents using the CLI/API. ([AWS Documentation][8])

---

# 21. MFA Delete Caveat

Current AWS documentation notes:

```text
MFA Delete
cannot be used with Lifecycle configurations.
```

([AWS Documentation][7])

So if your protection strategy heavily relies on:

```text
automatic Lifecycle expiration
```

MFA Delete needs careful architectural evaluation.

For enterprise immutability, S3 Object Lock is often the more important capability.

---

# 22. Object Lock

Now we move from:

```text
"Recover deleted data."
```

to:

```text
"Prevent protected object versions
from being deleted in the first place."
```

Amazon S3 Object Lock implements:

# WORM

```text
Write Once
Read Many
```

Object Lock can prevent protected object versions from being overwritten or deleted for a defined period or indefinitely through legal holds. ([AWS Documentation][9])

---

# 23. Object Lock Requires Versioning

Object Lock works on:

```text
OBJECT VERSIONS
```

Therefore Versioning must be enabled.

Current S3 supports enabling Object Lock on new **or existing** general-purpose buckets, provided the relevant configuration requirements are met. Once Object Lock is enabled on a bucket, AWS says you cannot disable Object Lock or suspend Versioning for that bucket. ([AWS Documentation][10])

This is an important modern update if you remember old tutorials claiming Object Lock could only be enabled when the bucket was created.

---

# 24. Object Lock Protects Versions — Not the Key Name

This is subtle.

Suppose:

```text
invoice.pdf

Version A
locked until 2033
```

Can you upload:

```text
another invoice.pdf
```

with the same key?

Yes.

S3 creates:

```text
Version B
```

The protected Version A remains locked.

Object Lock does not prevent additional versions or delete markers from being created above the protected version. ([AWS Documentation][9])

Conceptually:

```text
invoice.pdf

V1 LOCKED
   │
   ▼
V2 NEW
   │
   ▼
Delete Marker

V1 remains protected underneath
```

---

# 25. Retention Period

Object Lock can protect a version until:

```text
RetainUntilDate
```

Example:

```text
Object created:
2026-08-14

Retention:
7 years

Retain until:
2033-08-14
```

During the protection period, deletion behavior depends on the chosen retention mode. ([AWS Documentation][9])

There are two modes:

```text
Governance
Compliance
```

---

# 26. Governance Mode

Governance Mode protects objects from most users.

```text
Normal user
     │
DeleteObjectVersion
     │
     X
   blocked
```

But specially authorized principals can bypass the retention using the appropriate governance-bypass permission/process.

AWS positions Governance Mode as useful when you need strong protection but retain controlled administrative override capability. ([AWS Documentation][9])

Mental model:

```text
GOVERNANCE
=
locked

BUT

authorized break-glass override exists
```

---

# 27. Compliance Mode

Compliance is much stricter.

During its retention period:

```text
ordinary user
     X

administrator
     X

AWS account root user
     X
```

A protected version can't be deleted, its retention mode can't be changed, and its retention period can't be shortened. ([AWS Documentation][9])

Mental model:

```text
COMPLIANCE
=
NO BYPASS
until retention expires
```

### Serious warning

Do not experiment with long Compliance retention in a bucket containing disposable lab data.

If you lock data for:

```text
10 years
```

you have intentionally made it undeletable for that retention period.

---

# 28. Governance vs Compliance

| Governance                               | Compliance                       |
| ---------------------------------------- | -------------------------------- |
| Strong protection                        | Maximum retention protection     |
| Authorized bypass possible               | No retention bypass              |
| Good for internal controls               | Regulatory/WORM scenarios        |
| Can be overridden with special authority | Retention can't be shortened     |
| Useful for testing policies              | Treat as irreversible for period |

([AWS Documentation][9])

### Memory trick

```text
Governance
=
guarded door with emergency key


Compliance
=
door sealed until timer expires
```

---

# 29. Default Bucket Retention

Instead of specifying retention separately on every object, you can configure a bucket default.

Example:

```text
Default Object Lock:

Mode:
GOVERNANCE

Duration:
30 days
```

Every newly uploaded version automatically gets:

```text
RetainUntilDate
=
creation time + 30 days
```

unless an explicit per-version retention setting overrides it. ([AWS Documentation][9])

This is much safer than expecting application developers to remember retention headers manually.

---

# 30. Legal Hold

Legal Hold solves a different problem.

Retention period:

```text
protect until a date
```

Legal Hold:

```text
protect until somebody
explicitly removes the hold
```

A legal hold has **no expiration date**. ([AWS Documentation][11])

Example:

```text
customer-contract.pdf

LegalHold = ON
```

It remains protected until:

```text
LegalHold = OFF
```

by an authorized principal.

---

# 31. Retention and Legal Hold Can Coexist

An object version can have:

```text
Governance/Compliance retention

AND

Legal Hold
```

Think of two locks:

```text
Object Version
    │
    ├── Retention lock
    │
    └── Legal hold
```

Removing one doesn't necessarily make the object deletable if the other still protects it.

---

# 32. Ransomware Protection Mental Model

Imagine attacker obtains powerful application credentials.

Without protection:

```text
DELETE
DELETE
DELETE
DELETE
```

Versioning:

```text
creates delete markers
```

unless attacker also has version-deletion rights.

Governance Object Lock:

```text
harder to destroy protected versions
```

Compliance:

```text
retained versions cannot be deleted
during retention even by root
```

A strong protection architecture could be:

```text
S3 Versioning
     │
     ▼
Object Lock
     │
     ▼
cross-account replica/backup
     │
     ▼
restricted KMS administration
```

Object Lock is specifically intended for WORM/compliance and additional protection against object deletion/overwrite. ([AWS Documentation][12])

---

# 33. But Object Lock Doesn't Protect the KMS Key

This is extremely important.

Imagine:

```text
Object
LOCKED
until 2035
```

but it's encrypted with:

```text
customer-managed KMS key
```

If that KMS key is permanently deleted:

```text
Object still exists
Object still locked
BUT
data may become unreadable
```

AWS explicitly warns that Object Lock does not protect you from loss or deletion of the encryption key. ([AWS Documentation][13])

### Never forget

```text
Immutable encrypted data
+
deleted encryption key
=
immutably unreadable data
```

KMS governance is part of the data-protection architecture.

---

# 34. Object Lock + Lifecycle

Lifecycle still operates in Object Lock buckets.

For example, Lifecycle may:

```text
transition protected data
Standard
→ Glacier
```

That's allowed.

Lifecycle can also create delete markers according to normal versioning behavior.

But S3 Lifecycle cannot permanently delete a locked object version while retention/legal-hold protection remains active. ([AWS Documentation][13])

This is another example of:

```text
Lifecycle says DELETE

Object Lock says NO

Object Lock protection wins
```

# 35. S3 Replication

Now we move from:

```text
historical versions
```

to:

```text
another copy of data
```

S3 Replication automatically copies qualifying objects asynchronously from a source bucket to one or more configured destination buckets. ([AWS Documentation][14])

Two major categories:

```text
SRR
=
Same-Region Replication


CRR
=
Cross-Region Replication
```

---

# 36. Same-Region Replication — SRR

Architecture:

```text
ap-south-1

Source Bucket
      │
      │ replication
      ▼
Destination Bucket

same Region
```

Why?

Possible use cases:

```text
separate security account
separate analytics copy
different storage class
compliance boundaries
data aggregation
```

AWS supports replication between buckets in the same Region as well as across Regions. ([AWS Documentation][14])

---

# 37. Cross-Region Replication — CRR

Architecture:

```text
Mumbai
ap-south-1

Source Bucket
      │
      │ asynchronous replication
      ▼
Singapore
ap-southeast-1

Destination Bucket
```

Good for:

```text
regional DR
compliance copies
lower-latency regional consumers
geographic data protection
```

---

# 38. Replication Requires Versioning

This should be memorized:

```text
Source bucket:
Versioning ENABLED

Destination bucket:
Versioning ENABLED
```

Both source and destination must remain versioning-enabled for S3 replication. ([AWS Documentation][15])

Why?

Replication works at the:

```text
object version
```

level.

---

# 39. Replication Is Asynchronous

Suppose:

```text
10:00:00
PUT Mumbai/object.txt
```

Do not assume:

```text
10:00:00.001
Singapore definitely has it.
```

Standard replication is asynchronous.

Replication duration can vary depending on factors such as object size and Region pairing. ([AWS Documentation][16])

Therefore:

```text
CRR
≠
synchronous database replication
```

---

# 40. S3 Replication Time Control — RTC

If the business requires predictable replication behavior, S3 offers:

# Replication Time Control

Current AWS documentation states that S3 RTC provides an SLA for **99.99% of new objects to replicate within 15 minutes**, while most objects replicate in seconds. ([AWS Documentation][14])

Mental model:

```text
Normal CRR/SRR
=
asynchronous


RTC
=
asynchronous
+
predictable replication SLA
+
metrics/events
```

---

# 41. RTC Monitoring

With RTC, you can monitor replication using CloudWatch metrics and replication events.

Examples include signals when an object:

```text
misses the 15-minute threshold

or

replicates after the threshold
```

([AWS Documentation][17])

This lets operations teams alarm on:

```text
replication backlog / delay
```

rather than just assuming replication is healthy.

---

# 42. Versioning + CRR RPO Mental Model

Suppose:

```text
Primary Region
Mumbai

DR Region
Singapore
```

Replication lag:

```text
5 minutes
```

Then a regional disaster can potentially expose the latest few minutes of unreplicated data.

Therefore your DR design should think in:

```text
RPO
```

not merely:

```text
"CRR is enabled."
```

Replication does not equal zero-data-loss synchronization.

---

# 43. Does DELETE Replicate?

Important.

For modern replication rules, delete markers are **not necessarily replicated by default**.

You can configure delete-marker replication for eligible rules. ([AWS Documentation][18])

This is a crucial design choice.

---

# 44. Why You Might NOT Replicate Deletes

Suppose production accidentally does:

```bash
aws s3 rm \
  s3://primary/customer.db
```

If delete-marker replication is:

```text
DISABLED
```

then:

```text
Primary:
looks deleted

DR:
still has current copy
```

This can provide another recovery layer.

But it also means:

```text
source and destination
aren't exact logical mirrors
```

So the correct behavior depends on your objective.

---

# 45. Why You Might Replicate Deletes

If your requirement is:

```text
Destination should mirror
logical source state
```

then delete-marker replication may be appropriate.

Architecture decision:

```text
DR backup-like copy?
        │
        └── maybe don't replicate deletes


Mirror?
        │
        └── replicate delete markers
```

Don't toggle this setting blindly.

---

# 46. Hard Deletes Are Different

Deleting a **specific version ID** in the source is a permanent version deletion.

S3 live replication does not simply treat every source hard-delete operation as something that destroys the corresponding destination version.

This separation can be valuable for data protection and prevents your replica from becoming a trivial synchronized destruction mechanism. AWS documents specific replication behavior for delete markers versus version deletions. ([AWS Documentation][18])

---

# 47. What About Existing Objects?

Suppose bucket already contains:

```text
10 million objects
```

Then today you enable:

```text
CRR
```

Do all old objects automatically get replicated?

A standard new replication rule primarily handles eligible changes/new versions after the rule becomes active.

For existing objects, AWS provides:

# S3 Batch Replication

to replicate existing objects or retry appropriate objects at scale. ([AWS Documentation][19])

Mental model:

```text
Live Replication
=
future eligible object activity


Batch Replication
=
existing/backfill objects
```

# 48. Replication IAM Role

Replication needs AWS permissions.

Conceptually:

```text
S3 Source
   │
   ▼
Replication Role
   │
   ├── read source version
   ├── read metadata/tags
   │
   ▼
Destination Bucket
   │
   ├── ReplicateObject
   ├── ReplicateDelete
   └── ReplicateTags
```

If permissions are wrong, objects can enter:

```text
FAILED
```

replication status.

AWS replication troubleshooting specifically highlights source permissions, destination permissions, versioning state, KMS keys and ownership as common failure points. ([AWS Documentation][16])

# 49. Replication Status

Individual source objects can expose replication status such as:

```text
PENDING

COMPLETED

FAILED
```

You can inspect metadata with:

```bash
aws s3api head-object \
  --bucket "$SOURCE_BUCKET" \
  --key path/object.txt
```

and look for replication-related metadata.

This is useful during production troubleshooting:

```text
"Replication enabled"
```

doesn't automatically mean:

```text
"Every object replicated successfully."
```

# 50. SSE-KMS Replication

This connects directly to Part 2.

Suppose source object is encrypted using:

```text
SSE-KMS
```

Now replication needs access to:

```text
source KMS key
```

and potentially:

```text
destination KMS key
```

depending on configuration.

AWS documents KMS permissions as a major replication requirement/failure point, including decrypt permissions on the source side and data-key/encryption authorization at the destination. ([AWS Documentation][20])

So:

```text
S3 replication policy correct
```

but:

```text
KMS key policy wrong
```

can produce:

```text
ReplicationStatus = FAILED
```

# 51. Cross-Account Replication

A strong DR design might be:

```text
Production Account
Account A
      │
      │ CRR
      ▼
Backup / DR Account
Account B
```

Cross-account replication requires the destination account to authorize the replication role/bucket relationship appropriately. SSE-KMS cross-account replication additionally requires correct KMS authorization. ([AWS Documentation][20])

This provides administrative isolation:

```text
Production credentials compromised
      │
      X
do not automatically equal
full control of DR account
```

assuming policies are designed correctly.

For modern destination buckets using:

# 53. Object Lock + Replication

Object Lock can also be combined with replication.

If the source bucket has Object Lock enabled, the destination used for replication of those locked objects must also support Object Lock, and S3 can replicate retention metadata and legal-hold information. ([AWS Documentation][13])

```text
Production Account
Source S3
Object Lock
      │
      │ replicate
      ▼
DR Account
Destination S3
Object Lock
```

This creates a much stronger immutable DR architecture.

# 69. Interview Question

> **What's the difference between S3 Versioning, Object Lock, Replication, and Backup?**

A strong answer:

> Versioning keeps multiple versions of the same object key and lets me recover from accidental overwrites and soft deletes. Object Lock protects specified object versions using WORM controls so they can't be deleted or overwritten during a retention period, with Governance and Compliance offering different levels of override protection. Replication asynchronously maintains copies in another S3 bucket, either in the same Region or another Region, but it isn't itself historical backup because unwanted changes can also be replicated depending on rule configuration. Backup provides separate managed recovery points and retention policies. In a high-value environment I'd often combine these controls rather than treating one as a replacement for the others. ([AWS Documentation][1])

That's an architect-level answer.

# 71. The 14 Rules to Permanently Remember

```text
1. Versioning preserves object history.

2. Every new PUT to the same key creates a new version.

3. DELETE without VersionId creates a delete marker.

4. Delete marker ≠ permanent deletion.

5. DeleteObject + VersionId permanently deletes that version.

6. Previous versions cost storage money.

7. Lifecycle should usually manage old versions.

8. Versioning ≠ immutability.

9. Object Lock provides WORM protection.

10. Governance has controlled bypass capability.

11. Compliance cannot be bypassed during retention.

12. Legal Hold has no automatic expiration.

13. S3 Replication requires Versioning on source and destination.

14. Replication ≠ backup.
```

And the most important distinction:

```text
VERSIONING
=
RECOVER a mistake


OBJECT LOCK
=
PREVENT protected-version destruction


REPLICATION
=
MAINTAIN another copy


BACKUP
=
RETAIN independent recovery points
```

# Module 15 — Observability

## Lesson 6: Alertmanager and Notification Routing

Alertmanager groups related alerts, routes them, suppresses duplicates, applies inhibition, and delivers notifications. Prometheus decides what is firing; Alertmanager decides how people are notified. ([Prometheus][1])

# 15.6.1 Routing tree

```yaml
route:
  receiver: operations-low-urgency
  group_by: [alertname, cluster, service]
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 4h
  routes:
    - matchers:
        - severity="page"
        - environment="production"
      receiver: production-pager
      continue: true
    - matchers:
        - team="todo"
      receiver: todo-chat

inhibit_rules:
  - source_matchers: [alertname="ClusterUnavailable"]
    target_matchers: [severity=~"warning|page"]
    equal: [cluster]
```

Order matters. `continue: true` sends matching alerts to subsequent routes. Inhibition reduces consequential noise; it must not hide an independent customer-impacting failure.

# 15.6.2 Receiver security

Store webhook tokens, SMTP credentials, and pager keys outside Git and deliver them through a secret manager. Restrict Alertmanager UI/API access because silences can suppress critical detection. Encrypt transport, log changes, and test credential rotation.

# 15.6.3 Silence vs inhibition

```text
silence     temporary operator-defined matchers; maintenance or known event
inhibition  automatic suppression based on another firing alert
mute timing scheduled notification suppression
```

Every silence needs an owner, reason, incident/change link, and expiry. Never create broad unbounded silences such as `severity=~".*"`.

# Beginner Level

# 15.6.6 Alertmanager in layman language

Imagine a hospital alarm desk.

Many sensors report problems, but the desk decides:

```text
Which team should receive the alarm?
Should related alarms be grouped?
Is a larger known outage already explaining smaller alarms?
Is approved maintenance active?
When should a reminder be sent?
Did the notification provider accept the message?
```

Prometheus is the sensor/rule evaluator.

Alertmanager is the routing and notification coordinator.

```text
Prometheus rule fires
        ↓
Alertmanager receives alert
        ↓
group + route + inhibit/silence
        ↓
pager/chat/email/webhook
```

---

# 15.6.7 Core terms

```text
route          tree deciding receiver and timing
receiver       notification integration configuration
grouping       combines related alert instances
inhibition     suppresses target alerts while source alert fires
silence        temporary matcher-based operator suppression
mute interval  scheduled notification suppression
resolved       condition no longer firing
```

Alertmanager does not fix the incident. It helps the correct responder receive useful, controlled notification.

---

# 15.6.8 Grouping

Without grouping:

```text
100 failed Pods → 100 notifications
```

With grouping:

```text
100 alert instances
grouped by cluster/service/alertname
→ one notification with affected instances
```

Choose group labels that represent one incident/owner. Grouping every region together may hide regional scope; grouping by Pod may create a storm.

Timing:

```text
group_wait      wait for related alerts before first notification
group_interval  wait before sending changes to an existing group
repeat_interval reminder interval for unchanged firing group
```

# Intermediate Level

# 15.6.9 Route-tree behavior

Routes are evaluated as a tree. A child route inherits values from its parent unless overridden.

Example:

```yaml
route:
  receiver: operations-ticket
  group_by: [alertname, cluster, service]
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 4h
  routes:
    - matchers:
        - environment="production"
        - severity="page"
      receiver: production-pager
      continue: true
    - matchers:
        - team="order"
      receiver: order-chat
```

`continue: true` allows matching to continue through later sibling routes. Without it, the first matching child normally stops sibling evaluation.

Default receiver must be intentional; it catches alerts that do not match a more specific child.

---

# 15.6.10 Inhibition

Example:

```text
ClusterUnavailable fires
        ↓
many workload target-down alerts also fire
```

Inhibition can suppress lower-level alerts in the same cluster:

```yaml
inhibit_rules:
  - source_matchers:
      - alertname="ClusterUnavailable"
      - severity="page"
    target_matchers:
      - severity=~"warning|page"
    equal: [cluster]
```

Do not inhibit independent customer-impacting conditions merely because a parent alert exists. The parent page and dashboard must preserve actionable scope.

---

# 15.6.11 Silences

A silence uses label matchers and a time window.

Good silence record:

```text
matcher: cluster="prod-a", alertname="NodeDrainExpected"
owner: engineer@example.invalid
reason: CHG-2026-1842 planned node maintenance
start/end: explicit UTC time
```

Bad silence:

```text
severity=~".*"
end: one year later
reason: noisy
```

Every silence needs exact scope, owner, change/incident link and expiry. A noisy alert should be redesigned, not permanently hidden.

# Real-world Hands-on Tutorial

# 15.6.12 Local Alertmanager configuration

Create `alertmanager/alertmanager.yml`:

```yaml
global:
  resolve_timeout: 5m

route:
  receiver: local-webhook
  group_by: [alertname, service]
  group_wait: 10s
  group_interval: 1m
  repeat_interval: 1h
  routes:
    - matchers:
        - severity="page"
      receiver: local-webhook

receivers:
  - name: local-webhook
    webhook_configs:
      - url: http://webhook-receiver:5001/alerts
        send_resolved: true
```

Never commit real pager, chat or SMTP secrets in plaintext. Use environment/secret-file mechanisms supported by the deployment and external secret delivery.

Validate with the Alertmanager image or installed `amtool`:

```bash
amtool check-config alertmanager/alertmanager.yml
```

# Break, Debug and Secure

# 15.6.15 Notification troubleshooting workflow

```text
1. Is the Prometheus expression true?
2. Is alert pending or firing?
3. Did Prometheus send it to Alertmanager?
4. Does Alertmanager show the alert?
5. Which route matched?
6. Is it silenced, inhibited or muted?
7. Did receiver integration attempt delivery?
8. Did provider accept/reject it?
9. Did the correct human device/channel receive it?
```

Do not start by restarting Alertmanager.

Failure labs:

```text
wrong matcher captures no alerts
earlier route captures alert unexpectedly
expired webhook credential
receiver DNS/network denied
silence broader than intended
inhibition missing equal cluster label
```

---

# 15.6.16 High availability

Alertmanager replicas form a cluster to coordinate notification state. Prometheus should send alerts to all configured Alertmanager instances rather than depend on one naive load-balanced destination.

Production checks:

```text
replicas span failure domains
peer communication works
Prometheus reaches every replica
receiver credentials are consistent and rotated
silence state behavior is understood
notification delivery metrics are monitored
```

HA reduces component failure risk; it does not make an external pager provider infallible. Test an alternative escalation path.

---

# 15.6.17 Security

Protect Alertmanager because an attacker with access may:

```text
create silences
view alert labels/annotations
discover internal services
alter notification routing if config access exists
trigger webhook integrations
```

Use SSO/access proxy, private networking, least privilege, audit, encrypted credential delivery, protected Git/config, scoped webhook endpoints and log redaction.

# 15.6.19 Interview answers and final checklist

## Silence vs inhibition?

> **A silence is a time-bounded operator-created matcher set, usually for maintenance or a known event. Inhibition is automatic suppression of target alerts while a related source alert is firing, such as suppressing instance symptoms during a cluster outage.**

## How do you prevent alert storms?

> **I alert at the user/service level, group by incident and ownership labels, inhibit consequential symptoms, deduplicate through HA Alertmanager, use appropriate timing, and fix noisy rules. I never depend on broad permanent silences.**

Checklist:

```text
□ Default and child routes are tested
□ Group labels match incident ownership
□ Continue behavior is intentional
□ Inhibition preserves independent impact
□ Silences require scope, owner, reason and expiry
□ Receiver credentials stay outside Git plaintext
□ Delivery failure is monitored
□ HA replicas and peer paths are tested
□ Alternative escalation exists
□ UI/API and config are protected
```

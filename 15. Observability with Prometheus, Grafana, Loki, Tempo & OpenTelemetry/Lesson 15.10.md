# Module 15 — Observability

## Lesson 10: Distributed Tracing with Tempo

A trace follows one request across process boundaries. A span represents one timed operation with parentage, status, attributes, and events. Tempo stores traces economically in object storage and integrates them with Grafana, metrics, and Loki. ([Grafana][1])

# 15.10.1 Trace anatomy

```text
trace checkout
├── HTTP POST /checkout                 420 ms
├── validate cart                        12 ms
├── inventory gRPC reservation          85 ms
├── payment HTTP authorization         290 ms
└── publish order event                  18 ms
```

Propagate W3C Trace Context across synchronous calls and message metadata. Give spans stable operation names such as `POST /checkout`, not raw paths such as `/orders/918273`.

# 15.10.2 Sampling

```text
head sampling → decision near trace start; predictable cost, limited outcome knowledge
tail sampling → decision after spans arrive; retains errors/slow traces, needs collector state
```

Always sampling every production trace may be unaffordable. Uniformly sampling can miss rare failures. Define policy for errors, high latency, critical routes, and baseline probability. Record sampling assumptions during investigations.

# 15.10.3 Tempo flow

```text
instrumented service
  ── OTLP ──► Collector
  ── OTLP ──► Tempo distributor/ingesters
  ──────────► object storage
Grafana/TraceQL ──► query frontend/queriers
```

Protect OTLP endpoints, authenticate tenants, encrypt transport, and set ingestion limits. Avoid sensitive span attributes.

# 15.10.4 Investigation lab

Instrument a request crossing API → worker → database. Introduce a 500 ms dependency delay. Locate the trace from a latency exemplar, identify the critical span, then pivot from trace ID to logs.

Useful TraceQL concept:

```traceql
{ resource.service.name = "todo-api" && status = error }
```

Adapt query syntax and attributes to the installed Tempo release and telemetry schema.

# 15.10.5 Failure checks

```text
missing spans → propagation, sampling, exporter, queue, clock, shutdown flush
broken parentage → context not injected/extracted
no search result → attribute not retained/indexed or time/tenant mismatch
high cost → excessive span volume/attributes/retention
```

# 15.10.6 Beginner mental model: one parcel, many checkpoints

Imagine tracking a parcel from a shop to a sorting center, an airport, a local depot, and finally a customer. The tracking number identifies the whole journey. Each checkpoint records one part of it.

Distributed tracing uses the same model:

```text
trace ID  = the complete request journey
span ID   = one operation/checkpoint
parent ID = the operation that caused this one
```

A metric can tell you that checkout became slow. A trace can show that the payment child span consumed 290 ms of a 420 ms request. Logs can then explain the dependency's safe error details. These signals complement one another.

# 15.10.7 Span anatomy in plain language

A useful span normally contains:

| Part | Meaning | Example |
|---|---|---|
| Name | Stable operation | `POST /checkout` |
| Trace/span IDs | Correlation and identity | generated hexadecimal IDs |
| Parent | Causal relationship | server span is parent of DB span |
| Start/end | Timing | 10:20:31.100–10:20:31.142 |
| Kind | server, client, producer, consumer, internal | `SERVER` |
| Attributes | Searchable operational context | route, method, status |
| Events | Important moment inside the operation | exception recorded |
| Status | Explicit operation outcome | unset/OK/error by convention |
| Resource | The entity producing it | service name/version/environment |

Do not put passwords, authorization headers, raw SQL parameters, personal data, or unbounded payloads into attributes or events.

# 15.10.8 Context propagation

Instrumentation injects trace context into an outbound carrier and extracts it on the receiving side:

```text
HTTP:    traceparent/tracestate headers
message: approved metadata/property fields
gRPC:    protocol metadata
```

The W3C `traceparent` format carries a version, trace ID, parent span ID, and flags. Application code should use maintained OpenTelemetry propagators rather than hand-building the header.

Do not confuse **baggage** with trace identity. Baggage is application-defined context propagated downstream. It can create privacy, size, and trust problems, so keep it minimal, validate incoming values, and never use it for secrets.

# 15.10.9 Synchronous versus asynchronous causality

For a direct request, parent/child often represents causality well:

```text
API server span
  └── payment HTTP client span
```

For messaging, one producer event may be processed later, retried, batched, or consumed by several services. Decide deliberately between a parent relationship and a span link based on the semantic convention and processing model:

```text
producer span ── context in message ──> consumer processing span
                                         ├── retry attempt
                                         └── database span
```

Record queue latency separately from processing latency. Otherwise a “slow consumer” trace may actually show a message waiting in the queue.

# 15.10.10 Instrumentation strategy

Start with automatic instrumentation for supported HTTP, framework, database, and messaging libraries. Then add manual spans only for meaningful business operations:

```text
Good manual span: reserve_inventory
Good manual span: calculate_shipping_quote
Poor manual span: validateVariable
Poor manual span: every small function
```

Too few spans hide critical boundaries. Too many increase cost and make traces unreadable. A span deserves to exist when its timing, outcome, or causality helps an operator make a decision.

# 15.10.11 Sampling mathematics and bias

At 2,000 requests/second, retaining every request creates:

```text
2,000 traces/s × 10 spans/trace = 20,000 spans/s
```

With 5% probabilistic head sampling, approximately 1,000 spans/s remain, but an incident affecting 0.01% of requests can still be missed or poorly represented. Tail sampling can retain error, slow, or policy-matched traces after seeing more of the trace, but it needs state, consistent trace routing, memory, and a decision wait period.

Sampling policy should state:

- baseline probability for normal traffic;
- treatment of errors and high latency;
- critical routes or tenants, without exposing sensitive identity;
- maximum throughput/cost guardrails;
- what happens when the sampler is overloaded;
- how analysts account for sampling bias.

# 15.10.12 Tempo architecture from beginner to production

In a small lab, Tempo can run as one process. Production commonly separates roles:

```text
OTLP traffic
  -> distributor (receive, validate, spread)
  -> ingester (build live trace blocks)
  -> object storage (durable blocks)

queries
  -> query frontend (split/cache/schedule)
  -> querier (search live and stored data)
  -> object storage / ingesters

optional supporting roles
  -> compactor, metrics generator, caches
```

Exact deployment modes and components depend on the Tempo release. Treat object-store permissions, retention, tenant identity, and topology as part of the application—not infrastructure trivia.

# 15.10.13 Real hands-on: generate a two-service trace

Use two small services in a language you already know. The logical flow is:

```text
client -> todo-api GET /todos/{id}
             -> inventory-api GET /items/{id}
             -> simulated database operation
```

Set stable resources on each process:

```text
service.name=todo-api or inventory-api
service.version=lab-1
deployment.environment.name=lab
```

Enable supported auto-instrumentation, export OTLP to a local Collector, and export from the Collector to Tempo. Pin compatible, reviewed versions rather than copying `latest` into a reproducible lab.

A minimal Collector trace route looks like:

```yaml
receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
      http:
        endpoint: 0.0.0.0:4318

processors:
  memory_limiter:
    check_interval: 1s
    limit_mib: 256
  batch: {}

exporters:
  otlp/tempo:
    endpoint: tempo:4317
    tls:
      insecure: true  # disposable local network only

service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [memory_limiter, batch]
      exporters: [otlp/tempo]
```

Production must use authenticated and encrypted transport appropriate to its trust boundary.

# 15.10.14 Verify propagation, not just trace arrival

Make one request and inspect its tree in Grafana:

```text
one trace ID across both services
server and client spans connected correctly
stable route-based span names
dependency operation is a child or linked span as designed
HTTP/database semantic attributes are present
error outcome follows the instrumentation convention
no secret or raw user data appears
```

Two separate traces arriving in Tempo is not success. It proves export works but propagation is broken.

# 15.10.15 Add latency and find the critical path

Introduce a controlled 500 ms delay in `inventory-api`. Send normal and delayed requests, then compare:

```text
end-to-end duration
parent span duration
inventory client/server spans
database span
overlap between child operations
```

The longest span is not automatically the root cause. Analyze the **critical path**: the chain that determines the request's wall-clock completion. Parallel child spans can be individually long without adding their full durations together.

# 15.10.16 TraceQL investigation patterns

The exact TraceQL features available depend on the installed Tempo version. These examples illustrate the investigation intent:

```traceql
# Traces containing an error span for a service.
{ resource.service.name = "todo-api" && status = error }

# Slow spans for an operation.
{ resource.service.name = "inventory-api" && name = "GET /items/{id}" && duration > 500ms }

# Structural idea: checkout traces whose descendant contains an error.
{ name = "POST /checkout" } >> { status = error }
```

Begin with service, time, and known behavior. Broad attribute searches across long ranges cost more and may be limited. Save a validated query with the runbook if responders depend on it.

# 15.10.17 Metrics, exemplars, logs, and traces together

An industry-ready investigation might flow as follows:

```text
Prometheus: P95 latency alert for POST /checkout
  -> Grafana: histogram panel shows bad time window
  -> exemplar: jump to one representative trace
  -> Tempo: payment span dominates critical path
  -> trace_id: query structured logs around exact request
  -> deployment annotation: new payment client released 8 minutes earlier
```

Correlation fields must be consistent. Put trace and span IDs in structured logs, expose exemplars where libraries/backend support them, and use stable service/environment attributes across all signals.

# 15.10.18 Break it: propagation and shutdown

Perform two deliberate failures:

**Failure A—remove context injection.** The downstream service produces a new trace. Diagnose by inspecting outbound headers, inbound extraction, propagator configuration, proxies, and allowlists.

**Failure B—exit immediately after work.** Short-lived jobs may terminate before batches export. Compare graceful SDK/provider shutdown with forced termination and count exported spans.

Never “fix” missing spans by blindly setting sampling to 100%. First establish whether creation, propagation, sampling, queuing, export, tenancy, or query time is responsible.

# 15.10.19 Break it: partial traces and tail-sampling pressure

Block one service's exporter and observe partial traces. Then, in an isolated test environment, raise trace concurrency against a tail-sampling Collector. Watch decision wait, number of traces in memory, late spans, dropped spans, queue utilization, and collector memory.

A tail sampler needs all spans for a trace to reach the same decision-making instance or coordinated routing layer. Load balancing individual spans without trace affinity can fragment decisions.

# 15.10.20 Security, cost, and governance

Create an attribute allowlist for high-risk instrumentation. Review:

```text
HTTP query strings and headers
database statements and parameters
RPC metadata
messaging payloads
exception messages and stack traces
end-user and tenant identifiers
baggage propagated to downstream systems
```

Control who can search traces, enforce tenant isolation, encrypt transport and storage paths, set retention, and audit access. Sampling is a cost control, not a privacy control: a sampled trace can still contain prohibited data.

# 15.10.21 Production readiness checklist

- Stable resource attributes and operation names are documented.
- Context crosses HTTP, gRPC, messaging, and async boundaries used by the system.
- Sampling policy has cost, overload, rare-error, and critical-route behavior.
- Collector queues and Tempo ingestion/query components are observable.
- Object-store access, retention, encryption, and recovery are tested.
- TraceQL queries used in runbooks are version-tested.
- Metrics-to-trace and trace-to-log pivots work.
- PII/secret controls have automated tests.
- Load, rolling upgrade, zone failure, and partial-trace behavior are known.

# 15.10.22 Certification and interview preparation

This lesson supports trace fundamentals, context propagation, semantic attributes, OTLP pipelines, sampling, troubleshooting, and backend operations found across OpenTelemetry-focused learning and certification paths. Verify the current official objectives before sitting an exam.

**Beginner: What is a trace?**  The end-to-end representation of a request or transaction, made of causally related spans.

**Intermediate: Head versus tail sampling?**  Head sampling decides near the start and is cheaper/predictable; tail sampling decides after observing spans and can retain errors or slow traces but needs state and consistent routing.

**Intermediate: Why use stable span names?**  Raw IDs in names create unbounded values, poor grouping, higher cost, and difficult queries. Use route templates or operation names.

**Senior: Why are two services showing two traces for one request?**  Export works, but context was not injected, forwarded, or extracted; verify configured propagators and the carrier across every hop.

**Senior: Does an error log guarantee span status is error?**  No. Logging and span status are separate operations. Instrumentation must classify and record outcomes consistently.

**Expert: How do you find the root cause of a slow trace?**  Inspect the critical path, dependency timing, concurrency, errors/events, retries, and correlated deployment/log/metric evidence. The visually longest span alone is insufficient.

**Architect: How do you control trace cost without hiding rare incidents?**  Combine bounded instrumentation, baseline sampling, policy retention for errors/latency/critical flows, capacity limits, pipeline telemetry, and periodic checks for sampling bias.

**Never-forget answer:** tracing shows causality and time across boundaries. Propagation creates the story, sampling decides which stories remain, and safe stable attributes make them searchable.

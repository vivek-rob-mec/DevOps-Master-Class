# Lesson 8.7 — GitLab CI Production Pipeline

# Version → Test → Docker Build → Registry Push → Trivy Scan → SBOM → Provenance → Release Metadata → Staging Deploy → Manual Production Deploy → Rollback Metadata

In Lesson 8.6, you learned GitLab CI fundamentals.

Now we build the **production-style GitLab CI version** of your pipeline.

This pipeline mirrors what we already built for:

```text id="lnu1uk"
GitHub Actions
Jenkins
```

Now for:

```text id="mnk83k"
GitLab CI/CD
```

GitLab pipelines are defined in `.gitlab-ci.yml`; jobs run on GitLab Runners, and jobs can use Docker images as their execution environment when the runner supports the Docker executor. GitLab artifacts preserve files generated by jobs, while dotenv report artifacts can pass generated variables such as image tags between jobs. ([GitLab Docs][1])

# 3. Important GitLab Concepts Used

This production pipeline uses:

```text id="hhc0xu"
stages
jobs
rules
needs
artifacts
dotenv reports
Docker-in-Docker
GitLab Container Registry
manual production jobs
environments
protected variables
protected runners
```

GitLab’s docs distinguish cache and artifacts: cache is for reusable dependencies, while artifacts are job outputs that can be downloaded or passed to later jobs. Dotenv artifacts specifically collect variables from a file and expose them to later jobs in the same pipeline. ([GitLab Docs][2])

---

# 4. Docker-in-Docker Warning

This pipeline uses Docker-in-Docker for building and pushing images:

```yaml id="bmpujc"
image: docker:27
services:
  - docker:27-dind
```

GitLab documents Docker-in-Docker as a pattern where a job uses Docker tools and a Docker daemon service, usually requiring privileged runner mode. GitLab also warns that privileged containers should be isolated and restricted, especially for self-managed runners. ([GitLab Docs][3])

Production rule:

```text id="d2wrra"
Only trusted protected branches/tags should use privileged Docker build runners.
```

# 5. Required GitLab Project Settings

In GitLab, configure these before real production use:

```text id="em7f3x"
Settings
  -> CI/CD
    -> Variables
```

Recommended variables:

```text id="w9ux01"
BASE_VERSION
  value: 0.8.0
  protected: optional

PRODUCTION_ROLLBACK_VERSION
  value: previous known-good tag
  protected: true

STAGING_URL
  value: https://staging.example.com
  protected: optional

PRODUCTION_URL
  value: https://example.com
  protected: true
```

GitLab CI/CD variables can store reusable values and avoid hardcoding values in `.gitlab-ci.yml`; protected variables are only passed to pipelines running on protected branches or protected tags. Environment-scoped variables can also be used for environment-specific deployment values. ([GitLab Docs][4])

# 6. Protected Production Environment

For production, use GitLab environments.

GitLab protected environments restrict who can deploy to sensitive environments. GitLab also supports protected manual jobs through protected environments, so only authorized users can run production deployment jobs where supported by your GitLab tier. ([GitLab Docs][5])

Recommended setup:

```text id="drpjai"
Settings
  -> CI/CD
  -> Protected environments
  -> production
  -> allowed deployers: Maintainers / release managers
```

Professional rule:

```text id="n9si8k"
Production deployment should be protected by both pipeline rules and environment permissions.
```

# 9. Create Full GitLab Production Pipeline

Create:

```bash id="xevgal"
nano gitlab/production/pipelines/.gitlab-ci.production.yml
```

Paste:

```yaml id="s109zm"
stages:
  - validate
  - test
  - version
  - build
  - scan
  - evidence
  - deploy

variables:
  APP_DIR: "05-application-runtime/demo-node-api"
  SERVICE_NAME: "demo-node-api"
  DEFAULT_BASE_VERSION: "0.8.0"
  NODE_ENV: "test"
  DOCKER_TLS_CERTDIR: "/certs"
  DOCKER_DRIVER: "overlay2"

workflow:
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
    - if: '$CI_COMMIT_BRANCH == "main"'
    - if: '$CI_COMMIT_TAG'
    - if: '$CI_PIPELINE_SOURCE == "web"'
    - when: never

default:
  interruptible: true

cache:
  key:
    files:
      - 05-application-runtime/demo-node-api/package-lock.json
  paths:
    - 05-application-runtime/demo-node-api/.npm/

validate_context:
  stage: validate
  image: alpine:3.20
  script:
    - echo "Project: $CI_PROJECT_PATH"
    - echo "Pipeline: $CI_PIPELINE_ID"
    - echo "Pipeline source: $CI_PIPELINE_SOURCE"
    - echo "Branch: ${CI_COMMIT_BRANCH:-}"
    - echo "Tag: ${CI_COMMIT_TAG:-}"
    - echo "Commit: $CI_COMMIT_SHA"
    - echo "Short SHA: $CI_COMMIT_SHORT_SHA"
    - echo "Registry image: $CI_REGISTRY_IMAGE"

node_tests:
  stage: test
  image: node:22-alpine
  needs:
    - validate_context
  before_script:
    - node --version
    - npm --version
  script:
    - cd "$APP_DIR"
    - npm ci --cache .npm --prefer-offline
    - npm test
    - mkdir -p ../../08-cicd-pipelines/gitlab/production/reports
    - |
      cat > ../../08-cicd-pipelines/gitlab/production/reports/test-evidence.json <<EOF
      {
        "service_name": "$SERVICE_NAME",
        "ci_system": "gitlab-ci",
        "pipeline_id": "$CI_PIPELINE_ID",
        "job_id": "$CI_JOB_ID",
        "commit_sha": "$CI_COMMIT_SHA",
        "short_sha": "$CI_COMMIT_SHORT_SHA",
        "test_status": "passed",
        "created_at": "$(date -u +"%Y-%m-%dT%H:%M:%SZ")"
      }
      EOF
  artifacts:
    when: always
    expire_in: 14 days
    paths:
      - 08-cicd-pipelines/gitlab/production/reports/test-evidence.json

compute_version:
  stage: version
  image: alpine:3.20
  needs:
    - node_tests
  script:
    - |
      BASE_VERSION="${BASE_VERSION:-$DEFAULT_BASE_VERSION}"

      if [ -n "${CI_COMMIT_TAG:-}" ]; then
        VERSION="${CI_COMMIT_TAG#v}"
        CHANNEL="stable"
      elif [ "${CI_COMMIT_BRANCH:-}" = "main" ]; then
        VERSION="$BASE_VERSION-dev"
        CHANNEL="dev"
      else
        SAFE_REF="$(echo "$CI_COMMIT_REF_NAME" | tr '/' '-' | tr -cd 'a-zA-Z0-9._-')"
        VERSION="$BASE_VERSION-$SAFE_REF"
        CHANNEL="branch"
      fi

      DEPLOY_TAG="$VERSION-$CI_COMMIT_SHORT_SHA"
      IMAGE_REF="$CI_REGISTRY_IMAGE:$DEPLOY_TAG"

      {
        echo "VERSION=$VERSION"
        echo "CHANNEL=$CHANNEL"
        echo "DEPLOY_TAG=$DEPLOY_TAG"
        echo "IMAGE_REF=$IMAGE_REF"
        echo "SHORT_SHA=$CI_COMMIT_SHORT_SHA"
      } > build.env

      cat build.env
  artifacts:
    reports:
      dotenv: build.env
    paths:
      - build.env
    expire_in: 14 days

docker_build_push:
  stage: build
  image: docker:27
  services:
    - name: docker:27-dind
      alias: docker
  needs:
    - job: compute_version
      artifacts: true
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
      when: never
    - if: '$CI_COMMIT_BRANCH == "main"'
    - if: '$CI_COMMIT_TAG'
    - if: '$CI_PIPELINE_SOURCE == "web"'
  before_script:
    - docker version
    - echo "$CI_REGISTRY_PASSWORD" | docker login "$CI_REGISTRY" -u "$CI_REGISTRY_USER" --password-stdin
  script:
    - cd "$APP_DIR"
    - |
      docker build \
        -f Dockerfile.industry \
        --target runtime \
        --build-arg APP_VERSION="$DEPLOY_TAG" \
        --build-arg COMMIT_SHA="$SHORT_SHA" \
        -t "$IMAGE_REF" \
        .
    - docker push "$IMAGE_REF"
    - cd "$CI_PROJECT_DIR"
    - mkdir -p 08-cicd-pipelines/gitlab/production/reports
    - |
      cat > 08-cicd-pipelines/gitlab/production/reports/build-evidence.json <<EOF
      {
        "service_name": "$SERVICE_NAME",
        "image_ref": "$IMAGE_REF",
        "deploy_tag": "$DEPLOY_TAG",
        "commit_sha": "$CI_COMMIT_SHA",
        "build_status": "passed",
        "push_status": "passed",
        "created_at": "$(date -u +"%Y-%m-%dT%H:%M:%SZ")"
      }
      EOF
    - cat 08-cicd-pipelines/gitlab/production/reports/build-evidence.json
  artifacts:
    when: always
    expire_in: 14 days
    paths:
      - 08-cicd-pipelines/gitlab/production/reports/build-evidence.json

trivy_scan:
  stage: scan
  image:
    name: aquasec/trivy:latest
    entrypoint: [""]
  needs:
    - job: compute_version
      artifacts: true
    - job: docker_build_push
      artifacts: true
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
      when: never
    - if: '$CI_COMMIT_BRANCH == "main"'
    - if: '$CI_COMMIT_TAG'
    - if: '$CI_PIPELINE_SOURCE == "web"'
  variables:
    TRIVY_NO_PROGRESS: "true"
    TRIVY_CACHE_DIR: ".trivycache/"
  cache:
    key: trivy-cache
    paths:
      - .trivycache/
  before_script:
    - mkdir -p 08-cicd-pipelines/gitlab/production/reports
  script:
    - trivy image --severity HIGH,CRITICAL --format json --output "08-cicd-pipelines/gitlab/production/reports/trivy-scan-$DEPLOY_TAG.json" "$IMAGE_REF"
    - |
      cat > scan.env <<EOF
      SCAN_STATUS=passed
      SCAN_REPORT=08-cicd-pipelines/gitlab/production/reports/trivy-scan-$DEPLOY_TAG.json
      EOF
    - cat scan.env
  artifacts:
    when: always
    expire_in: 14 days
    reports:
      dotenv: scan.env
    paths:
      - scan.env
      - 08-cicd-pipelines/gitlab/production/reports/trivy-scan-*.json

generate_sbom:
  stage: evidence
  image:
    name: aquasec/trivy:latest
    entrypoint: [""]
  needs:
    - job: compute_version
      artifacts: true
    - job: docker_build_push
      artifacts: true
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
      when: never
    - if: '$CI_COMMIT_BRANCH == "main"'
    - if: '$CI_COMMIT_TAG'
    - if: '$CI_PIPELINE_SOURCE == "web"'

    - trivy image --format spdx-json --output "08-cicd-pipelines/gitlab/production/sbom/spdx/$SERVICE_NAME-$DEPLOY_TAG.spdx.json" "$IMAGE_REF"
    - |
      cat > sbom.env <<EOF
      SBOM_CYCLONEDX=08-cicd-pipelines/gitlab/production/sbom/cyclonedx/$SERVICE_NAME-$DEPLOY_TAG.cdx.json
      SBOM_SPDX=08-cicd-pipelines/gitlab/production/sbom/spdx/$SERVICE_NAME-$DEPLOY_TAG.spdx.json
      EOF
    - cat sbom.env
  artifacts:
    when: always
    expire_in: 30 days
    reports:
      dotenv: sbom.env
    paths:
      - sbom.env
      - 08-cicd-pipelines/gitlab/production/sbom/

deploy_production_manual:
  stage: deploy
  image: alpine:3.20
  needs:
    - job: release_metadata
      artifacts: true
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
      when: manual
    - if: '$CI_COMMIT_TAG'
      when: manual
    - when: never
  allow_failure: false
  environment:
    name: production
    url: ${PRODUCTION_URL}
  before_script:
    - apk add --no-cache jq
  script:
    - |
      if [ -z "${PRODUCTION_ROLLBACK_VERSION:-}" ]; then
        echo "ERROR: PRODUCTION_ROLLBACK_VERSION is required for production deployment" >&2
        exit 1
      fi

      case "$IMAGE_REF" in
        *:latest|*:prod|*:production|*:stable)
          echo "ERROR: refusing mutable production tag: $IMAGE_REF" >&2
          exit 1
          ;;
      esac
    - mkdir -p 08-cicd-pipelines/gitlab/production/deployments
    - |
      cat > "08-cicd-pipelines/gitlab/production/deployments/production-$DEPLOY_TAG.json" <<EOF
      {
        "service_name": "$SERVICE_NAME",
        "environment": "production",
        "artifact": "$IMAGE_REF",
        "deploy_tag": "$DEPLOY_TAG",
        "release_metadata": "$RELEASE_METADATA",
        "rollback_version": "$PRODUCTION_ROLLBACK_VERSION",
        "approved_by": "$GITLAB_USER_LOGIN",
        "deployment_status": "manual_placeholder_success",
        "created_at": "$(date -u +"%Y-%m-%dT%H:%M:%SZ")"
      }
      EOF
    - jq . "08-cicd-pipelines/gitlab/production/deployments/production-$DEPLOY_TAG.json"
  artifacts:
    when: always
    expire_in: 90 days
    paths:
      - 08-cicd-pipelines/gitlab/production/deployments/
      - 08-cicd-pipelines/gitlab/production/release-records/
```

# 10. Important Production Note About `aquasec/trivy:latest`

The pipeline uses:

```yaml id="js389h"

  name: aquasec/trivy:latest
```

For learning, this is okay.

For production, pin a version or digest:

```yaml id="zl8iq3"
image:
  name: aquasec/trivy:<approved-version>
```

or:

```yaml id="ynzxnm"
image:
  name: aquasec/trivy@sha256:<digest>
```

Professional rule:

```text id="wwyedc"
Do not use floating tool images in high-control production pipelines unless your organization intentionally accepts that risk.
```

````markdown id="7zv2p3"
# GitLab CI Production Pipeline Runbook

## Safe First Run

Use the pipeline on a non-production branch first.

Expected jobs:

- validate_context
- node_tests
- compute_version

The Docker push jobs only run on main, tags, or web pipeline according to rules.

## Main Branch Run

On `main`, expected flow:

```text
validate -> test -> version -> build/push -> scan -> evidence -> staging deploy placeholder
````

## Production Run

Production deployment is manual:

```text
deploy_production_manual
```

Before running it, set:

```text
PRODUCTION_ROLLBACK_VERSION=<previous-known-good-tag>
```

## Evidence

Download artifacts from:

* `node_tests`
* `docker_build_push`
* `trivy_scan`
* `generate_sbom`
* `create_provenance`
* `release_metadata`
* `deploy_production_manual`

## Rollback

Production deployment record contains:

```text
rollback_version
```

Use that tag to restore the previous known-good artifact.

## Do Not

* deploy `latest`
* rebuild for production
* expose production variables to unprotected branches
* run production deploy on untrusted runners
* use privileged runners for untrusted code

# 28. Interview Explanation

## What does your GitLab production pipeline do?

Strong answer:

```text id="o2rb33"
My GitLab CI production pipeline validates context, runs Node.js tests, computes an immutable version-SHA tag, builds and pushes a Docker image to GitLab Container Registry, scans the image with Trivy, generates CycloneDX and SPDX SBOMs, creates provenance and release metadata, deploys to staging as a placeholder, and provides a manual production job that requires rollback metadata.
```

## How do you pass variables between GitLab jobs?

Strong answer:

```text id="h3gu9b"
I generate a dotenv file such as `build.env`, save it as an `artifacts:reports:dotenv` artifact, and then downstream jobs use `needs` with artifacts enabled so the computed values become available as CI/CD variables.
```

## Why use `needs`?

Strong answer:

```text id="ao4qva"
`needs` defines explicit job dependencies and can pass artifacts from one job to another. It also allows pipelines to run faster than strict stage-by-stage execution when jobs do not depend on every earlier job.
```

## Why is Docker-in-Docker risky?

Strong answer:

```text id="ygyj6x"
Docker-in-Docker often requires privileged runners, which increases risk because privileged containers have powerful host-level capabilities. I restrict Docker build runners to trusted projects, protected branches, and isolated ephemeral machines where possible.
```

## How do you protect production in GitLab CI?

Strong answer:

```text id="52fonz"
I use manual production jobs, protected environments, protected variables, protected runners, immutable image tags, rollback metadata, and deployment records. Production jobs should run only for trusted branches or tags and by authorized users.
```

## Cache vs artifacts?

Strong answer:

```text id="9ab72f"
Cache is for dependencies like npm packages to speed up future jobs. Artifacts are generated outputs such as reports, SBOMs, release metadata, provenance, and deployment records that must be preserved or passed between jobs.
```

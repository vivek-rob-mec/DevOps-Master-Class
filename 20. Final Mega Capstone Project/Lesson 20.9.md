# 20.9.2 Incident process

Declare based on customer/business impact. Assign IC, operations, communications, and scribe. Freeze unsafe release progression, preserve UTC timeline/evidence, prefer reversible containment, communicate facts/unknowns/next update, and validate complete journeys before closure.

# 20.9.3 DR architecture

Primary production runs multi-AZ. A separate recovery account/region holds reproducible IaC, replicated images, recoverable secrets/keys according to policy, and database/object backups or replication that meet RPO.

```text
declare → fence old writers/controllers
→ provision/activate pinned regional platform
→ restore/promote data
→ restore identity/secrets/config
→ validate integrity
→ shift controlled traffic
→ observe backlog and SLO
→ plan failback
```

List dependencies: Git, registry, DNS, certificates, identity, KMS, secrets, monitoring, payment provider, and communications.

# 20.9.4 Required game days

1. One node lost.
2. One Availability Zone lost.
3. Database writer failover.
4. Bad canary plus schema expansion.
5. Pager provider unavailable.
6. GitOps management cluster lost.
7. Primary region isolated during writes.
8. Restore detects backup integrity problem.

Measure MTTD, declaration, containment, mitigation, full recovery, RTO/RPO, data discrepancy, communication, and manual steps.

# 20.9.5 Postmortem

# 20.9.13 Game day A: bad rollout plus migration

New version burns checkout SLO; old version is not compatible with the latest migration. Strong response declares, pauses rollout, protects data, chooses feature disable/forward fix or verified compatible recovery, communicates uncertainty, and validates SLI/data. Add expand-contract gate.

# 20.9.14 Game day B: database brownout

20% slow DB calls trigger retry amplification and pool exhaustion. Diagnose via SLI/traces/pools/attempt metrics, contain with deadlines/concurrency/circuit/load shedding/retry budget, restore, drain backlog, and verify business consistency.

# 20.9.15 Game day C: zone loss at peak

Remove one-zone capacity during rollout. Validate topology/PDB/scheduling/node/IP/volume/database/network, remaining critical capacity, traffic, user SLI, and recovery. Record whether capacity model was correct.

# 20.9.16 Game day D: regional disaster

Complications:

```text
replication lag near RPO
secondary quota below peak
old writer reachable from automation
DNS clients cache
central Grafana in failed region
```

Exercise evidence/declaration, load shedding, quota, fencing, promotion, staged routing, independent monitoring, integrity/backlog, communication, and later failback.

# 20.9.17 Game day E: pager/telemetry failure

SLO burns while provider rejects pages and metrics pipeline is partially missing. Independent edge/business/canary evidence and fallback communication must declare incident. Restore page/telemetry, quantify blind window/missed alerts, and improve independence.

# 20.9.18 Postmortem requirements

Quantify impact, timeline, trigger/preconditions/failed defenses/amplifiers/response constraints, what worked, and strong prevention/detection/containment/recovery actions. Each action has owner/date/risk/evidence/review. Track recurring classes.

# 20.9.19 Toil and automation

Record simulated quarter pages/tickets/manual operations. Select one toil task, eliminate cause or build detector -> dry run -> bounded idempotent automation with least privilege, audit, partial failure, stop, and measured toil reduction.

# 20.9.20 Acceptance checklist

- Catalog/owner/SLO/alert/runbook/access/on-call are executable.
- Pages are symptom/action and delivery tested.
- Incident roles/communication/change ledger work in drills.
- Backup restores authoritative business state and dependencies.
- Regional failover fences writers and measures RPO/RTO.
- Zone/brownout/migration/blindness scenarios preserve safety.
- Recovery includes backlog/data/source-of-truth reconciliation.
- Postmortem actions have verified risk reduction.
- Pager/toil load is measured and sustainable.

# 20.9.21 Certification and interview preparation

This lesson consolidates SRE, cloud reliability, Kubernetes, incident, and DR concepts. Match it to current official curricula.

**Beginner: HA versus DR?**  HA continues through selected failures; DR restores service after larger loss.

**Intermediate: RTO versus RPO?**  Maximum acceptable recovery duration versus lost history measured in time.

**Intermediate: Mitigated versus resolved?**  User service restored/contained versus underlying cause and temporary risk removed.

**Senior: How lead regional incident?**  Declare/roles, protect data, verify/fence authority, ensure capacity/dependencies, promote/route gradually, validate integrity/SLI, communicate, reconcile/fail back later.

**Senior: How prove backup?**  Isolated restore, business invariant/checksum/journey validation, actual RPO/RTO, evidence.

**Expert: Telemetry and paging fail during outage—what now?**  Use predesigned independent user/business/provider signals, fallback communication, low-dependency diagnostics, cautious changes, then restore/reconcile blind interval.

**Architect: How make SRE sustainable?**  Ownership/objectives/error-budget, quality paging/on-call staffing, executable runbooks, incident learning, toil reduction, capacity/resilience/DR tests, and leadership priority.

**Never-forget answer:** operations is proven when an unfamiliar responder can detect, coordinate, mitigate, communicate, restore data/service, and learn within tested objectives.

# 20.9.22 Professional completion evidence

Hand the operations package to a responder who did not build Atlas. Without private coaching, they must acknowledge a synthetic page, declare and assign roles, follow a runbook, make one bounded mitigation, communicate an update, validate the original SLI, and identify the recovery-data procedure. Record access gaps, unsafe ambiguity, and time at each stage. The lesson passes only after those gaps are repaired and a second run demonstrates improvement; an author successfully following their own notes is not sufficient operational proof.

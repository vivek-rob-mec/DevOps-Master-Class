# Module 18 — Platform Engineering

## Lesson 6: Kubernetes Platform and Multi-tenancy

# 18.6.1 Tenant model

```text
soft multi-tenancy  teams share cluster/control plane; policy isolates
harder isolation    separate clusters/accounts for stronger boundaries
hybrid              shared non-prod, dedicated critical/regulatory prod
```

Choose by trust, regulation, blast radius, scale, regional needs, cost, and operational capacity. A namespace is useful isolation, not a universal security boundary.

# 18.6.2 Platform baseline

```text
cluster lifecycle and upgrades
node classes/autoscaling
ingress, DNS, certificates
workload identity and secrets
policy/admission and RBAC
network policy
storage classes and backup
observability and audit
GitOps and progressive delivery
resource quotas and cost allocation
```

Separate platform foundation from tenant workloads through AppProjects/repositories, namespaces, identities, and policy.

# 18.6.3 Workload contract

Require owner, environment, resource requests/limits policy, health probes, graceful termination, disruption tolerance, topology, immutable image, non-root security, network intent, secret references, telemetry, and SLO tier.

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-budget
spec:
  hard:
    requests.cpu: "20"
    requests.memory: 40Gi
    limits.cpu: "40"
    limits.memory: 80Gi
    pods: "100"
```

# 18.6.4 Isolation tests

Prove a tenant cannot:

```text
read another namespace's Secrets
create cluster-scoped RBAC
use privileged host access
bypass approved registries
reach denied tenant networks
consume unlimited resources
alter platform GitOps objects
```

Test policy with negative cases in CI and a disposable cluster.

# 18.6.5 Upgrade and lifecycle

Publish supported Kubernetes versions, node/runtime classes, APIs, add-ons, deprecation dates, and migration automation. Canary upgrades with representative workloads, then progress by environment and risk tier.

# 18.6.6 Lab

Design dev and regulated-prod tenant classes. Specify accounts/clusters, namespaces, RBAC, network, policy, quotas, nodes, secret access, logging, GitOps boundary, and cost. Defend why the isolation differs.

# 18.6.7 Beginner mental model: apartments need more than nameplates

Putting two families in apartments with different door labels does not isolate them if locks, electricity limits, plumbing, and building access are shared without control. A Kubernetes namespace is an organizational boundary, not complete security or resource isolation by itself.

# 18.6.8 Choose the tenant and threat model

A tenant may be a team, application, business unit, customer, or trust class. Ask:

```text
Are tenants mutually trusted, semi-trusted, or hostile?
Can users create arbitrary pods/controllers/webhooks/CRDs?
Do data or regulatory rules require stronger boundaries?
What noisy-neighbor impact is acceptable?
Who administers nodes/cluster-scoped resources?
```

Hostile or regulated tenants may require separate clusters/accounts, not only namespaces.

# 18.6.9 Cluster tenancy models

| Model | Strength | Cost/tradeoff |
|---|---|---|
| Shared cluster/namespaces | efficiency and simple fleet | larger shared blast radius |
| Cluster per environment/team | stronger isolation/customization | fleet cost/operations |
| Cluster per trust/data class | strong governance boundary | capacity fragmentation |
| Virtual cluster | tenant control abstraction | additional components/limitations |

Use a small number of well-defined classes rather than one-off clusters without lifecycle ownership.

# 18.6.10 Identity and RBAC

Map corporate/workload identity to namespaces and resources. Use groups, least privilege, separate admin roles, and short-lived credentials.

Avoid:

```text
wildcard verbs/resources for application teams
cluster-admin in CI
shared ServiceAccounts across services
long-lived kubeconfigs
permission to create privilege-escalating RBAC
```

Test privilege escalation through RoleBinding, impersonation, secrets, pods, and admission/config resources.

# 18.6.11 Workload isolation baseline

```text
Pod Security Admission/profile
non-root, no privilege escalation, controlled capabilities
read-only filesystem where practical
seccomp and approved runtime classes
image provenance/registry policy
hostPath/hostNetwork/hostPID restrictions
service-account token handling
admission policy with exceptions
```

Security context fields must match application needs and be tested; copied restrictions can break workloads or create fake compliance.

# 18.6.12 Network isolation

Default-deny ingress and egress where the networking implementation enforces it, then allow required DNS, telemetry, dependencies, control planes, and external endpoints.

Test from attacker and legitimate pods. NetworkPolicy behavior depends on the cluster networking implementation; policy YAML alone is not proof.

# 18.6.13 Resource fairness

Use:

```text
ResourceQuota per namespace/tenant
LimitRange defaults/bounds
requests and limits with platform policy
PriorityClass carefully controlled
autoscaling quotas and node pools
API rate/admission fairness
storage/network/external-service quotas
```

CPU/memory quotas do not control database connections, log volume, cloud API calls, or expensive queries. Budget all shared dependencies.

# 18.6.14 Namespace lifecycle

Provision through the platform with owner, environment, data class, cost allocation, TTL/lifecycle, quotas, policy, network, secret identity, GitOps boundary, and observability.

Deletion must discover PVCs, cloud load balancers, DNS, snapshots, secrets, finalizers, external databases, retention, and legal hold. “Delete namespace” can leave expensive or sensitive resources behind.

# 18.6.15 Cluster-scoped resources

CRDs, webhooks, StorageClasses, ClusterRoles, PriorityClasses, and operators affect many tenants. Restrict creation/changes to platform governance, test upgrade compatibility, and define ownership.

A broken admission webhook can block deployments cluster-wide. Configure failure policy and availability from risk, not convenience.

# 18.6.16 Real hands-on: tenant baseline

Create synthetic namespaces `team-a` and `team-b` through a versioned baseline containing:

```text
owner/cost/data labels
ResourceQuota and LimitRange
default-deny NetworkPolicy plus approved paths
Pod Security Admission labels/profile
team RBAC and workload ServiceAccount
GitOps Application/Project boundary
telemetry/cost attribution
```

Render and policy-test before applying to a disposable cluster.

# 18.6.17 Isolation tests

Attempt from Team A:

1. Read Team B ConfigMaps/Secrets.
2. Bind itself cluster-admin.
3. Run privileged/hostPath/hostNetwork pod.
4. Connect to Team B service without allow policy.
5. Exhaust CPU/memory/pods/PVC quota.
6. Use Team B cloud workload identity.
7. Deploy into Team B through GitOps.
8. Flood shared telemetry or database.

Verify denied actions, audit evidence, and legitimate allowed operations.

# 18.6.18 Noisy-neighbor lab

Create a safe CPU, memory, API, or telemetry load in Team A. Measure Team B scheduling/latency/SLO. Apply quotas, priority/fairness, node-pool isolation, or backend tenant limits and repeat.

Define when the tenant must graduate to stronger isolation.

# 18.6.19 Upgrade and fleet lifecycle

Maintain supported Kubernetes/add-on/API versions, compatibility tests, canary clusters/node pools, workload readiness, PDB/topology capacity, migration guides, and deprecation deadlines. Inventory API/resource usage before removal.

Test platform baseline changes against representative tenant workloads and adversarial isolation cases.

# 18.6.20 Shared responsibility and support

Platform owns cluster control/add-ons, baseline policy, tenant provisioning, upgrades, shared observability, and platform incidents. Teams own workload code, requests/probes, app secrets usage, SLO/runbook, dependency behavior, and policy-compliant manifests.

Exceptions name owner, risk, compensating control, scope, and expiry.

# 18.6.21 Certification and interview preparation

Multi-tenancy, RBAC, workload/network security, quotas, and lifecycle are common Kubernetes/platform certification topics. Verify current Kubernetes features and objectives.

**Beginner: Is a namespace a security boundary?**  It scopes names and many policies/RBAC, but complete isolation also needs identity, workload, network, resource, cloud, and cluster-scoped controls.

**Intermediate: What does ResourceQuota protect?**  Selected namespaced object/resource consumption; it does not cover every external/shared dependency.

**Intermediate: Why default-deny networking?**  Begin with no unapproved pod communication and explicitly allow required paths, provided the network implementation enforces it.

**Senior: When use separate clusters?**  Strong trust/regulatory/data/control-plane isolation, incompatible lifecycle/customization, or blast-radius/capacity needs justify cost.

**Senior: What are dangerous cluster-scoped resources?**  RBAC, CRDs/operators, admission webhooks, storage/priority classes and similar changes can affect every tenant.

**Expert: How do you prove isolation?**  Adversarial cross-tenant, privilege, network, identity, quota, GitOps, cloud, and shared-backend tests plus audit—not YAML review alone.

**Architect: How do you manage a cluster fleet?**  Standard classes/baselines, declarative provisioning, inventory, canary upgrades, compatibility/policy tests, SLOs, exceptions, cost/capacity, and decommission automation.

**Never-forget answer:** multi-tenancy is a threat and fairness design across identity, compute, network, data, control planes, and lifecycle—not a namespace naming convention.

# Module 20 — Final Mega Capstone Project

## Lesson 2: Requirements, ADRs and Repository Governance

# 20.2.1 Requirements package

Create:

```text
business journeys and actors
functional acceptance cases
SLIs/SLOs and severity tiers
traffic/data/cost assumptions
security and compliance obligations
RTO/RPO and failure model
ownership and support model
constraints, non-goals, and open risks
```

Assign stable IDs such as `REL-ORDER-001` so implementation and tests trace back to requirements.

# 20.2.2 Repository model

```text
atlas-apps/          service source and tests
atlas-infrastructure/ Terraform modules/stacks/policy
atlas-platform/      cluster add-ons, templates, platform APIs
atlas-config/        Argo Applications and environment desired state
atlas-observability/ dashboards, rules, collectors, runbooks
atlas-docs/          architecture, ADRs, operations, evidence index
```

Choose mono/multi-repository boundaries from ownership and change coupling. Separate artifact build from environment promotion.

# 20.2.3 Governance

Protect default branches. Require pull requests, CODEOWNERS, status checks, signed/verified identity according to policy, and review for sensitive paths.

```text
/terraform/prod/       @cloud-platform @security
/clusters/prod/        @platform-sre
/environments/prod/    @service-owner @release-manager
/policies/             @security-platform
/slo/                  @service-owner @sre
```

Use short-lived CI identity, secret scanning, dependency updates, and audit retention. Untrusted forks/PRs cannot access cloud or release credentials.

# 20.2.4 ADR set

At minimum:

```text
AWS account/region topology
EKS cluster/tenant model
database and consistency
event delivery/idempotency
CI and artifact provenance
GitOps repository/promotion
secret delivery
observability architecture
SLO and incident policy
DR strategy
cost allocation and commitment policy
```

# 20.2.6 Gate

No infrastructure begins until critical journeys, data authority, trust boundaries, SLOs, RTO/RPO, repositories, and ownership are reviewed. Record unknowns with an experiment and due date.

# 20.2.7 Requirement specification template

```yaml
id: FR-CHECKOUT-001
journey: submit checkout
statement: A valid authenticated cart can create one authoritative order
invariants:
  - one idempotency key creates at most one logical order
  - acknowledgement follows durable order persistence
quality:
  availability: 99.95%/30d
  latency: 99% under 500ms
security: tenant authorization and synthetic payment only
evidence:
  - automated contract/concurrency test
  - SLI recording rule and dashboard
owner: team-orders
```

Use unique IDs so tests, ADRs, runbooks, and risks can reference requirements.

# 20.2.8 Repository boundaries

Example:

```text
atlas-apps/          application source and telemetry contracts
atlas-platform/      templates, reusable workflows, policies
atlas-infrastructure Terraform modules/live account-region intent
atlas-gitops/        cluster/app desired state by environment
atlas-observability/ rules, dashboards, Collector config, runbooks
atlas-docs/          architecture, ADRs, threats, game-day evidence
```

One monorepo is also valid if ownership, release, permissions, and blast radius fit. Record why.

# 20.2.9 Branch and environment protection

For critical paths require reviewed changes, status/policy checks, CODEOWNERS, protected branches/environments, signed/verified identities as policy, and restricted admin bypass. Separate build from production promotion authority.

Test emergency process. A policy no administrator can bypass during an incident may be unsafe; an invisible permanent bypass is also unsafe.

# 20.2.10 CODEOWNERS limitations

CODEOWNERS helps request/require review under repository settings. It does not prove reviewers understood risk, protect external cloud state, or replace runtime authorization. Protect the CODEOWNERS file itself and ensure teams exist.

Sensitive paths:

```text
/terraform/live/production/ @platform-infra @security
/gitops/production/         @platform-gitops @service-owner
/policies/                  @platform-security
/migrations/                @data-platform @service-owner
```

# 20.2.11 Change classes

```text
standard: tested low-risk repeatable, automated gates
normal: peer review and staged rollout
high risk: data/security/region/shared platform, specialist approval/game plan
emergency: incident-authorized scoped change, audit, later reconciliation/review
```

Automate evidence and reserve human attention for real judgment.

# 20.2.12 Required ADRs

At minimum:

```text
account/network topology
EKS cluster/tenant strategy
database consistency and regional authority
event/outbox semantics
CI identity/provenance and artifact promotion
GitOps repository and rollback model
secret/workload identity
telemetry architecture and retention
SLO/error-budget and on-call
DR/fencing/failback
platform API/golden path
cost allocation/unit economics
```

Each contains context, requirements, options, decision, consequences, validation, owner, and revisit trigger.

# 20.2.13 Risk register

```yaml
risk: regional database writer loss
likelihood: low
impact: critical
correlation: identity/DNS/replication
prevention: multi-AZ, controlled changes
detection: write SLI and replication/RPO signals
containment: stop writes/load shed
recovery: fence/promote secondary
evidence: quarterly game day
owner: data-platform
residual_acceptance: named approver/date
```

Track security, cost, supplier, people, data, and operational risks.

# 20.2.14 Traceability matrix

| Requirement | Design/ADR | Implementation | Test | Operational evidence |
|---|---|---|---|---|
| FR-CHECKOUT-001 | ADR data/outbox | order-api | duplicate/commit crash | order SLI + reconciliation |
| NFR-DR-001 | ADR regional DR | Terraform/data config | regional game day | RTO/RPO report |
| SEC-ID-001 | ADR workload identity | ServiceAccount/IAM | stolen/static-key denial | audit |

Automate missing links where feasible but retain review of evidence quality.

# 20.2.15 Pull-request contract

Every material PR explains:

```text
why and linked requirement/risk
scope and affected owners/environments
rendered plan/diff and policy/test results
security/data/cost/SLO impact
rollout, observation, abort, rollback/forward fix
migration compatibility
evidence after deployment
```

Never paste secrets or sensitive production data into PRs.

# 20.2.16 Real hands-on repository bootstrap

Create the selected repositories/directories with README, ownership, contribution, ADR template/index, threat model, runbooks, issue/PR templates, version/release policy, CI validation, and artifact/evidence retention policy.

Open a synthetic production change and prove required reviewers/checks cannot be bypassed by a normal contributor.

# 20.2.17 Failure exercise: malicious or accidental governance change

Attempt to modify both a production policy and its CODEOWNERS requirement in one untrusted branch. Verify protection still requires independent authorized review and audit. Then simulate required reviewer unavailable; exercise time-bound emergency governance and reconciliation.

# 20.2.18 Documentation lifecycle

Assign owners and freshness signals for requirements, ADRs, diagrams, inventories, runbooks, recovery plans, and evidence. Link docs from catalog/alerts. Test commands and links during releases/game days.

Do not rewrite historical accepted ADRs silently; supersede them so decision history remains.

# 20.2.19 Exit gate

- Requirements are measurable, scoped, owned, and prioritized.
- Invariants and data/security obligations are explicit.
- Repositories/source-of-truth ownership do not overlap ambiguously.
- Protected change and emergency paths are tested.
- Required ADR/risk/threat documents exist with validation.
- Traceability links requirements to test/operation evidence.
- No secret or real customer data exists in repositories.
- All unresolved critical risks have accepted owner and next action.

# 20.2.20 Certification and interview preparation

Repository governance reinforces DevOps, IaC, security, and architecture competencies. Verify current SCM features and certification objectives.

**Beginner: What is an ADR?**  A record of architecture context, options, decision, consequences, validation, and revisit condition.

**Intermediate: What does CODEOWNERS do?**  Maps paths to responsible reviewers; enforcement depends on repository branch/ruleset configuration.

**Intermediate: Why traceability?**  It proves each requirement reaches design, implementation, test, and operation, exposing missing work.

**Senior: Monorepo or multirepo?**  Choose from ownership, release coupling, permissions, discovery, tooling, scale, and blast radius; both can work.

**Senior: How should emergency change work?**  Declared incident, scoped authorized action, audit/evidence, user validation, prompt source-of-truth reconciliation, access revocation, review.

**Expert: Can governance slow delivery?**  Poor governance can. Automate repeatable evidence and standard change, apply proportional controls, and focus humans on high-risk decisions.

**Architect: How do you prove documentation is trustworthy?**  Ownership, version/source, automated schema/link tests, operational exercises, incident feedback, and superseded decision history.

**Never-forget answer:** governance makes intent, authority, evidence, and recovery explicit. Trace every critical promise from requirement to tested production behavior.

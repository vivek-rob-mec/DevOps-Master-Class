# Module 20 — Final Mega Capstone Project

## Lesson 5: Application, Data and Event Architecture

# 20.5.1 Service boundaries

```text
catalog-api       owns product read model
order-api         owns order lifecycle and outbox
payment-adapter   owns provider protocol/idempotency mapping
fulfillment-worker consumes order events and reports status
```

Keep the initial system small enough to operate. Split only where ownership, scaling, security, or change boundaries justify it.

# 20.5.2 Order transaction

```text
POST /orders + Idempotency-Key
→ validate tenant/cart
→ transaction: create order + outbox event
→ return authoritative order ID
→ relay publishes OrderCreated
→ consumers process idempotently
```

Store request fingerprint and result for idempotency. Duplicate key with different request fails. The payment provider idempotency key maps durably to the order/payment attempt.

# 20.5.3 Data design

Use managed PostgreSQL for authoritative transactional state, cache only derived/read data, and object storage for immutable exports/evidence. Define schema constraints, indexes, retention, tenant key, encryption, backup/PITR, replica behavior, and regional recovery.

Use expand-and-contract migrations with immutable migration artifacts, locks, timeout, and separate credentials. Rollback application code must remain compatible with current schema.

# 20.5.4 Event design

```json
{
  "id":"uuid",
  "type":"OrderCreated",
  "version":1,
  "tenant_id":"tenant-a",
  "aggregate_id":"ord-123",
  "occurred_at":"UTC timestamp",
  "traceparent":"00-...",
  "data":{}
}
```

Define ordering per order, at-least-once handling, retries, DLQ/quarantine, schema compatibility, replay authorization, and PII minimization.

# 20.5.5 Application quality

Unit, contract, integration, migration, concurrency, idempotency, property/security, performance, and failure tests run in CI. The application emits RED metrics, structured correlated logs, traces across messaging, and business outcome metrics.

# 20.5.6 Failure exercises

```text
duplicate create request
lost response after committed order
duplicate payment callback
outbox relay restart
poison fulfillment event
database failover during transaction
cache outage at peak
old application version after schema expansion
```

Prove correct outcome, bounded retry load, evidence, and operator recovery.

# 20.5.7 Domain boundaries and ownership

```text
catalog owns product descriptions/price view for lab
cart owns mutable pre-order selection
order owns authoritative order lifecycle
inventory owns available/reserved stock
notification owns delivery attempts, not order truth
```

Services exchange APIs/events, not direct writes into another service's tables. Begin with fewer deployable units if team size cannot operate many microservices; the logical ownership model still applies.

# 20.5.8 Checkout invariant

```text
one authenticated idempotency key + normalized checkout request
-> at most one logical order
acknowledged order -> durable and retrievable
inventory cannot be silently oversold under declared policy
payment simulation cannot produce real financial side effect
events reflect committed authoritative state
```

Write these as automated concurrency and crash tests.

# 20.5.9 Checkout sequence

```text
client -> order-api: POST /orders + idempotency key
order-api -> validate identity/cart/version
order-api -> inventory: reserve with its own idempotent operation
order-api DB transaction: order + idempotency + outbox
order-api -> client: 201 with stable order ID
outbox publisher -> order event stream
worker -> notification and downstream projections
```

Define failure/compensation when inventory reservation succeeds but order commit fails.

# 20.5.10 Idempotency record

Store caller scope, key, request fingerprint, status, logical result, creation/expiry. Concurrent reuse uses a uniqueness constraint/lock. Same key with different payload returns a conflict rather than reusing unrelated result.

Do not log the entire sensitive request fingerprint material.

# 20.5.11 Database design

For order data use relational constraints/transactions unless requirements justify another model. Define primary/foreign/unique keys, tenant authorization, indexes from queries, partition/archive trigger, backups, encryption, RTO/RPO, and schema migration.

Read replicas/search projections may be stale; user/API behavior states freshness.

# 20.5.12 Outbox and consumer inbox

```text
transaction:
  write order state
  write Outbox(event_id, aggregate_id, version, payload)

publisher retries until broker accepts
consumer deduplicates event_id/consumer in same local transaction
```

Expose oldest unpublished outbox age, duplicate/stale event, consumer lag, DLQ, and replay.

# 20.5.13 Event contract

```json
{
  "event_id": "synthetic-01J",
  "event_type": "OrderCreated",
  "schema_version": 1,
  "occurred_at": "2026-08-15T10:20:31Z",
  "aggregate_id": "order-synthetic",
  "aggregate_version": 1,
  "tenant_id": "tenant-synthetic",
  "traceparent": "synthetic",
  "data": {"notification_reference": "safe-reference"}
}
```

Minimize sensitive content; authorize consumers and version compatibility.

# 20.5.14 Timeout, retry, and overload

Propagate an end-to-end deadline. Retry only transient safe/idempotent calls in a bounded deliberate layer with backoff/jitter/retry budget. Protect databases/providers through concurrency pools, circuit/load shedding, queue limits, and priority.

Count original operations, attempts, final outcomes, shed work, and authoritative business success separately.

# 20.5.15 Schema evolution

Use expand-contract and mixed-version tests:

```text
add compatible field/table/index
-> deploy dual-compatible code
-> backfill with checkpoint/rate/validation
-> switch behavior
-> observe rollback window
-> remove old later
```

Database migrations use explicit ordering/hooks and must not make automatic rollback corrupt or incompatible.

# 20.5.16 Real hands-on implementation

Build `order-api` and one worker in Python/Node/Java/Go:

- REST contract with authentication stub and resource authorization;
- idempotent checkout with database constraint;
- order/outbox transaction;
- publisher and idempotent consumer;
- structured logs and OpenTelemetry traces/metrics;
- readiness/startup/graceful shutdown;
- migrations and synthetic fixtures;
- unit, integration, contract, load, and crash tests.

# 20.5.17 Required crash matrix

Crash at:

```text
before inventory reserve
after reserve before order transaction
after DB commit before HTTP reply
after outbox read before broker acknowledgement
after consumer side effect before message acknowledgement
during graceful shutdown with batch in flight
```

Prove final invariant or a visible repair state for each.

# 20.5.18 Concurrency and ordering tests

Send 100 concurrent identical idempotency keys and verify one logical order. Send two different payloads with same key and verify conflict. Deliver duplicate/out-of-order events and verify consumer final state/version. Load a hot tenant/key and observe fairness/partition behavior.

# 20.5.19 Data/security tests

Attempt cross-tenant ID access, unauthorized order update, SQL/JSON injection, oversized body, malicious event schema, replay after dedup expiry, secret/header logging, and deletion with retention. Verify denial, safe audit, and no information disclosure.

# 20.5.20 Performance and resilience tests

Run baseline/peak/spike/soak with realistic read/write mix, then database brownout, queue outage/backlog, notification failure, pod/node loss, and rollout. Measure user SLI, critical path, pool/queue, retries, data correctness, and recovery.

# 20.5.21 Acceptance checklist

- Service/data ownership and invariants are documented.
- Checkout is idempotent under concurrency/timeout/crash.
- Database and event publication have no silent commit gap.
- Consumers tolerate duplicate/order/replay per contract.
- Migration supports mixed versions and safe recovery.
- Deadline/retry/concurrency/load shedding protect dependencies.
- Auth/tenant/data/telemetry security tests pass.
- Load/failure meets objective and final data reconciles.
- RTO/RPO backup/restore is tested later in capstone.

# 20.5.22 Certification and interview preparation

This lesson covers API, data, messaging, resilience, testing, and security system design. Map provider-specific implementation to current exams.

**Beginner: Why idempotency key?**  A client can safely retry an uncertain timeout without creating duplicate logical order.

**Intermediate: What does transactional outbox solve?**  The local business commit and event-to-publish are recorded atomically, eliminating one major commit/publish gap.

**Intermediate: Why can duplicates still happen?**  Publisher/consumer acknowledgement can fail after successful processing; idempotent consumers remain necessary.

**Senior: What if inventory reserves but order commit fails?**  Use idempotent release/expiry or saga compensation and visible reconciliation; define business state rather than pretending a global rollback.

**Senior: How deploy schema changes safely?**  Expand, mixed-version-compatible code, controlled backfill/switch, observe, contract later.

**Expert: How do you prove exactly-once business outcome?**  Define boundary, atomic/idempotent state transitions, unique constraints/dedup, crash tests, and reconciliation; broker label alone is insufficient.

**Architect: Microservices or modular monolith?**  Choose from domain/team/scale/deployment/failure needs and operating capacity. Distributed boundaries add network/data/incident cost.

**Never-forget answer:** protect business invariants across timeouts, retries, crashes, duplicates, migrations, and partial side effects; make every incomplete state visible and repairable.

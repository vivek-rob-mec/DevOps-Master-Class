# Module 15 — Observability

## Lesson 3: Metrics, Labels and PromQL

# 15.3.1 Metric types

```text
Counter   monotonically increases; use rate/increase
Gauge     current value may rise or fall
Histogram counts observations in buckets and exposes sum/count
Summary   calculates client-side quantiles; difficult to aggregate
```

Name units explicitly: `_seconds`, `_bytes`, `_total`. Use labels for bounded dimensions, never raw user IDs, request IDs, email addresses, or arbitrary URLs.

# 15.3.2 PromQL foundations

```promql
# target availability
up{job="todo-api"}

# request rate by status class
sum by (status_class) (
  rate(http_server_requests_total{service="todo-api"}[5m])
)

# error ratio
sum(rate(http_server_requests_total{service="todo-api",status_class="5xx"}[5m]))
/
sum(rate(http_server_requests_total{service="todo-api"}[5m]))

# p95 latency from a histogram
histogram_quantile(
  0.95,
  sum by (le) (rate(http_server_request_duration_seconds_bucket{service="todo-api"}[5m]))
)
```

Aggregate first with the labels required by the question. Preserve `le` for classic histogram quantiles. Protect ratios against missing traffic when using them in alert rules.

# 15.3.3 Vector matching

PromQL binary operations match series by labels. `on(...)`, `ignoring(...)`, `group_left`, and `group_right` change that matching. Many believable but incorrect dashboards come from accidental many-to-many joins or dropped dimensions.

```promql
sum by (namespace, pod) (rate(container_cpu_usage_seconds_total[5m]))
/
on (namespace, pod) group_left
sum by (namespace, pod) (kube_pod_container_resource_requests{resource="cpu"})
```

Validate units and label cardinality on each side before trusting the result.

# 15.3.5 Never-forget rules

1. A label set is a series identity.
2. Counters need `rate()` or `increase()`.
3. Average latency hides tails.
4. Missing data is not automatically zero.
5. Query correctness includes units, window, population, and label matching.

# Beginner Level

# 15.3.6 Metric model in layman language

Imagine a grocery shop records sales like this:

```text
product="milk", branch="pune", payment="card" → 120 sales
product="milk", branch="mumbai", payment="cash" → 85 sales
```

The measured thing is sales. Product, branch and payment are dimensions used to filter and group it.

Prometheus works similarly:

```text
http_requests_total{
  service="order-api",
  environment="production",
  route="/orders",
  method="POST",
  status_class="2xx"
}
```

One metric name plus one complete label set identifies one time series.

Changing any label value creates another series.

```text
metric name + label names/values = series identity
timestamp + value                = sample
```

---

# 15.3.7 Counter deeply understood

A counter records cumulative events.

```text
09:00 requests_total = 100
09:01 requests_total = 160
```

The useful question is usually not:

```text
What is the raw total since the process started?
```

It is:

```text
How quickly is it increasing?
```

PromQL:

```promql
rate(http_requests_total[5m])
```

`rate()` handles counter resets within the selected range.

Use:

```text
rate()     per-second average increase over a range
irate()    near-instant rate from last two samples; volatile
increase() estimated total increase over a range
```

Never apply `rate()` to CPU percentage, queue depth or another ordinary gauge.

---

# 15.3.8 Gauge deeply understood

A gauge represents current state and can rise or fall.

```text
queue_depth 40
queue_depth 62
queue_depth 18
```

Useful functions:

```promql
max_over_time(queue_depth[1h])
avg_over_time(queue_depth[1h])
min_over_time(queue_depth[1h])
```

A gauge may be stale if the producer stopped reporting. Always consider target health and timestamps.

---

# 15.3.9 Histogram deeply understood

Suppose five requests take:

```text
0.08s, 0.12s, 0.21s, 0.70s, 1.40s
```

A classic histogram exposes cumulative buckets:

```text
le="0.1"  → 1
le="0.25" → 3
le="1.0"  → 4
le="+Inf" → 5
```

It also exposes:

```text
_count → number of observations
_sum   → sum of observed values
```

Average duration:

```promql
sum(rate(request_duration_seconds_sum[5m]))
/
sum(rate(request_duration_seconds_count[5m]))
```

p95:

```promql
histogram_quantile(
  0.95,
  sum by (le) (
    rate(request_duration_seconds_bucket[5m])
  )
)
```

Classic histogram aggregation must preserve `le`.

Bucket choice controls accuracy around important thresholds. If the SLO is 300 ms but buckets jump from 250 ms to 1 second, the estimate near the objective is weak.

---

# 15.3.10 Summary vs histogram

```text
Histogram
→ server can aggregate buckets across replicas
→ quantile estimated at query time
→ bucket boundaries chosen during instrumentation

Summary
→ client calculates configured quantiles
→ quantiles generally cannot be meaningfully aggregated
→ quantiles fixed in the client
```

Choose from aggregation, accuracy, performance and objective needs. Do not select a summary only because the word “quantile” sounds convenient.

# Intermediate Level

# 15.3.11 Selectors

Instant vector:

```promql
up{job="order-api"}
```

Range vector:

```promql
order_api_http_requests_total[5m]
```

Matchers:

```promql
{environment="production"}  # equals
{environment!="production"} # not equals
{route=~"/api/.*"}          # regex match
{route!~"/health.*"}        # regex not-match
```

Begin with the smallest correct population. A query that silently mixes dev, QA and production may be syntactically valid but operationally wrong.

---

# 15.3.12 Aggregation across dimensions

Total request rate by service:

```promql
sum by (service) (
  rate(http_requests_total[5m])
)
```

Remove instance while preserving other labels:

```promql
sum without (instance, pod) (
  rate(http_requests_total[5m])
)
```

`by` keeps only listed grouping labels.

`without` removes listed labels and keeps the rest.

Always decide which dimensions the result must retain before writing `sum()`.

---

# 15.3.13 Error ratios and zero traffic

Naive ratio:

```promql
sum(rate(http_requests_total{status_class="5xx"}[5m]))
/
sum(rate(http_requests_total[5m]))
```

Problem:

```text
What if denominator is zero?
What if only health traffic exists?
What if invalid requests should be excluded?
```

Production recording/alert logic should define eligible traffic and require enough volume:

```promql
(
  sum(rate(http_requests_total{route!="/healthz",status_class="5xx"}[5m]))
  /
  sum(rate(http_requests_total{route!="/healthz"}[5m]))
)
and
sum(rate(http_requests_total{route!="/healthz"}[5m])) > 1
```

The exact threshold belongs to service traffic and objective policy.

---

# 15.3.14 Vector matching

PromQL binary operations match label sets.

Example:

```promql
pod_cpu_usage
/
on (namespace, pod)
pod_cpu_request
```

If one side has an additional `container` label, matching may return no result or require a deliberate aggregation/join.

Modifiers:

```text
on(...)       match using only listed labels
ignoring(...) ignore listed labels
group_left    allow many left series to match one right series
group_right   allow one left series to match many right series
```

Many-to-many matching is rejected because the result would be ambiguous.

Before using group modifiers, print and understand label sets on each side.

---

# 15.3.15 Missing series and staleness

Prometheus marks series stale when targets stop exposing them or disappear. A missing result is different from a numeric zero.

Sometimes you intentionally combine absence with zero-valued target metadata:

```promql
rate(http_requests_total{status_class="5xx"}[5m])
or
up * 0
```

This pattern must preserve compatible labels and semantics. Do not mechanically convert every absence to zero; scrape failure would then look like healthy zero errors.

# Expert Level

# 15.3.16 Naming and units

Good names:

```text
http_server_requests_total
http_server_request_duration_seconds
process_resident_memory_bytes
queue_oldest_message_age_seconds
```

Rules:

```text
include base unit
use _total for counters where convention applies
do not mix milliseconds and seconds
do not encode label values into metric names
reserve colon style for recording-rule results
```

Prefer:

```text
http_responses_total{status_class="5xx"}
```

over:

```text
http_500_responses_total
http_503_responses_total
```

# 15.3.17 Cardinality budget

Estimate before release:

```text
series ≈ metrics × instances × product of label cardinalities
```

Example:

```text
1 metric
50 Pods
20 routes
5 status classes
3 methods
= 15,000 possible series
```

Add customer ID and the model collapses.

Professional controls:

```text
telemetry contract
allowed label values
normalized routes/errors
CI instrumentation review
active-series dashboards
scrape/sample limits
backend tenant limits
release canary
cost allocation
```

# Interview Preparation

# 15.3.24 Beginner-to-expert answers

## Counter vs gauge?

> **A counter accumulates and normally only increases until reset, so I use rate or increase to interpret it. A gauge represents current state and can increase or decrease, such as queue depth or active connections.**

## Histogram vs summary?

> **Histograms count observations in buckets and can be aggregated across replicas before estimating quantiles. Summaries can calculate client-side quantiles but those quantiles usually cannot be meaningfully aggregated. I choose based on aggregation, objective thresholds, accuracy and cost.**

## Why is my PromQL ratio empty?

> **I inspect numerator and denominator separately, label sets, time range, scrape health, staleness and vector matching. Common causes are zero/no traffic, one side missing, mismatched dimensions or an over-specific selector. I do not convert absence to zero until the semantics are explicit.**

## How do you prevent cardinality incidents?

> **I create a label contract, normalize routes and errors, prohibit request/user IDs, estimate series before release, monitor active series and ingestion, enforce limits, and canary instrumentation changes. Unique investigation IDs belong in logs or traces.**

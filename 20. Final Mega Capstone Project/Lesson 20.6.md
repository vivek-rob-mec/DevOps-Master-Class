# Module 20 — Final Mega Capstone Project

## Lesson 6: CI, DevSecOps and Software Supply Chain

# 20.6.1 Pipeline

```text
pull request
→ lint/unit/secret/dependency/SAST/IaC tests
→ protected merge
→ hermetic/reproducible build where feasible
→ integration/security tests
→ SBOM + provenance + signature
→ immutable ECR digest
→ config promotion pull request
```

CI proposes deployable state; Argo deploys from Git. Never run `kubectl apply` from the build job for normal production delivery.

# 20.6.2 Identity and isolation

Use OIDC federation with trust bound to repository, ref/environment, audience, and workflow context. Separate PR validation from trusted release. Use ephemeral isolated runners or hardened pools, least-privilege network/secret access, bounded jobs, and audited role sessions.

# 20.6.3 Evidence

For every artifact preserve:

```text
source revision and review
builder/workflow identity
tests and security results
dependency lock and SBOM
provenance/attestation
signature
registry digest
promotion and deployment records
```

Define retention and access. A scan report alone does not prove which digest reached production.

# 20.6.4 Gate policy

```text
critical tests pass
no prohibited secret exposure
approved base/build image
vulnerability/license policy satisfied or expiring exception
SBOM/provenance/signature present
artifact digest immutable
production config reviewed by owners
```

Policy failures provide actionable remediation. Exceptions specify artifact/scope, risk, compensating control, approvers, and expiry.

# 20.6.5 Required attacks/failures

1. Malicious fork requests cloud token.
2. Build dependency is replaced unexpectedly.
3. Base image has critical vulnerability.
4. Artifact tag is overwritten.
5. Signature verification fails.
6. Registry is unavailable after build.
7. Runner tries to access production network.
8. Promotion PR references digest not produced by trusted workflow.

# 20.6.6 Acceptance

Demonstrate one immutable digest promoted from dev to QA to production, with no rebuild, complete evidence, enforced separation, and a safe rollback/revert path.

# 20.6.7 Threat model the build

Attackers may control source changes, dependencies, build scripts, pull requests, caches, runner images, artifacts, registry credentials, reusable workflows, or deployment metadata.

```text
source trust -> build isolation -> dependency trust
-> artifact identity/provenance -> registry integrity
-> promotion authorization -> admission/runtime verification
```

# 20.6.8 Pipeline contract

```text
pull request: no privileged secrets, fast quality/security evidence
trusted merge: isolated build, tests, SBOM/provenance, immutable publish
promotion: config PR references digest and evidence
deployment: GitOps/admission verifies and observes
release: runtime digest/revision/customer SLI correlated
```

Build once; promote the same digest.

# 20.6.9 CI identity

Use OIDC/federation with conditions on organization/repository/workflow/ref/environment/audience as provider supports. Grant separate least-privilege roles for pull request, artifact publish, config proposal, and deployment reconciliation.

No static AWS keys in CI secrets. Keep default repository token permissions minimal.

# 20.6.10 Runner isolation

Use ephemeral runners or strong job isolation; prevent privileged host socket reuse, cross-job workspace/cache/secrets, unrestricted egress, and untrusted persistent state. Patch and attest runner images, restrict who registers runners, and observe capacity/abuse.

Fork/untrusted code runs in a nonprivileged context.

# 20.6.11 Dependency and build controls

```text
lock files and controlled registries/proxies
checksum/signature verification where supported
dependency update automation and review
reproducible/hermetic goals where feasible
secret/static/dependency/license/container/IaC scans
test fixtures for malicious package/build behavior
```

Scanner findings require risk policy, triage, exception, and expiry—not blind failure or blind ignore.

# 20.6.12 SBOM, provenance, and signing

Generate SBOM and provenance from the trusted build, associate them with immutable digest, and sign/attest through approved identity/keyless or key-managed approach. Verify at promotion/admission.

Consult the current SLSA spec before stating a build level. SBOM/provenance do not prove code is vulnerability-free.

# 20.6.13 Reusable workflow

```yaml
jobs:
  verify:
    permissions:
      contents: read
    steps:
      - run: unit-and-contract-tests
      - run: secret-sast-dependency-iac-policy
  build:
    permissions:
      contents: read
      id-token: write
    steps:
      - run: isolated-build
      - run: generate-sbom-provenance-and-publish-digest
```

This is conceptual, not a drop-in workflow. Use reviewed pinned actions and current syntax.

# 20.6.14 Promotion separation

CI does not directly mutate production clusters. It proposes a Git change containing artifact digest and deployment metadata. Authorized review/policy merges; Argo CD reconciles under its scoped cluster identity.

Emergency flow remains audited and reconciled to Git.

# 20.6.15 Real hands-on pipeline

Implement for `order-api`:

1. PR tests/code quality/API/schema/IaC/policy.
2. Trusted merge builds reviewed Dockerfile.
3. Create SBOM/provenance, scan, sign/attest.
4. Push immutable digest with restricted identity.
5. Open environment config PR referencing digest.
6. Verify evidence and deploy through Argo.
7. Emit release event with source/build/digest/config/runtime links.

# 20.6.16 Attack test: secret exfiltration

An untrusted PR attempts to print `DEMO_SECRET_NEVER_REAL`, access metadata/cloud role, and upload workspace. Verify no privileged secret/identity, restricted network/context, redacted logs, and denied promotion.

# 20.6.17 Attack test: artifact substitution

Approve one tag, then repoint it to another lab digest. Admission/promotion should rely on approved digest/signature/provenance and reject mismatch. Query runtime image ID and trace to source.

# 20.6.18 Attack test: poisoned cache/action

Attempt cross-branch cache poisoning and replace an unpinned third-party action/version. Verify trust separation, cache key/scope, pin/update governance, allowlist, and review. Record residual risk.

# 20.6.19 Failure test: scanner/provider outage

Decide by gate risk:

```text
mandatory critical production evidence unavailable -> queue/block
advisory low-risk check -> documented degraded policy
emergency patch -> accountable time-bound exception + compensating checks
```

Test status, user message, audit, recovery, and later reconciliation.

# 20.6.20 Fleet upgrade test

Change reusable workflow/build image on canary fixture repositories, including each language/runtime. Observe compatibility, duration, findings, artifacts, provenance, and rollback. Then create migration PRs and track unsupported consumers.

# 20.6.21 Acceptance checklist

- Trust contexts and identities are separate/short-lived/least privilege.
- Untrusted code cannot reach production secret/role/artifact path.
- Runners/caches/workspaces are isolated and governed.
- Dependency/action/builder sources and versions are controlled.
- Artifact has immutable digest plus current-policy evidence.
- Build-once promotion and GitOps separation are proven.
- Admission/runtime verifies intended artifact.
- Gate outage/exception and central workflow rollout are tested.
- Pipeline SLO, queue, support, audit, cost have owners.

# 20.6.22 Certification and interview preparation

This lesson maps to DevSecOps, AWS identity, GitHub/GitLab/Jenkins, container, SLSA, and Kubernetes policy competencies. Verify current official products/specs.

**Beginner: Why immutable digest?**  It identifies exact artifact bytes; tags can move.

**Intermediate: SBOM versus provenance?**  SBOM inventories components; provenance describes build source/process and identity.

**Intermediate: Why OIDC in CI?**  Exchanges verified workflow identity for short-lived scoped cloud credentials instead of stored long-lived keys.

**Senior: Why separate build and deploy?**  Reduce privilege/blast radius and make production promotion a distinct authorized, auditable desired-state change.

**Senior: How handle security scanner outage?**  Risk-specific block/queue/degrade/exception policy with compensating controls, ownership, expiry, and reconciliation.

**Expert: What does SLSA prove?**  Specific supply-chain properties under the exact current level/track requirements and scope—not overall application security.

**Architect: Design multi-tenant CI.**  Trust-class runner isolation, short-lived identities, minimal tokens, safe caches/artifacts/networks, quotas/fairness, controlled workflows, provenance, promotion separation, telemetry and incident response.

**Never-forget answer:** treat build code as untrusted, make artifacts immutable and attributable, separate promotion authority, and test the attack paths—not only happy builds.

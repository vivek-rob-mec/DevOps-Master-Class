# Module 15 — Observability

## Lesson 8: Loki and LogQL

Loki indexes labels and stores compressed log chunks. Unlike a full-text index of every field, its efficiency depends on using a small, bounded stream-label set and filtering content at query time. ([Grafana][1])

# 15.8.1 Label design

Good stream labels:

```text
cluster, namespace, workload, container, environment
```

Bad labels:

```text
trace_id, request_id, user_id, timestamp, raw URL
```

Put high-cardinality context in structured JSON log fields, not index labels. Normalize route templates rather than logging identifiers in paths.

# 15.8.2 LogQL essentials

```logql
{cluster="prod", namespace="todo-prod", app="todo-api"} |= "error"

{app="todo-api"} | json | level="error" | line_format "{{.trace_id}} {{.message}}"

sum by (status) (
  count_over_time({app="todo-api"} | json | __error__="" [5m])
)

quantile_over_time(
  0.95,
  {app="todo-api"} | json | unwrap duration_ms | __error__="" [5m]
)
```

Filter by indexed labels before expensive parsing. Check `__error__` after parsers and unwrap operations.

# 15.8.3 Structured logging contract

```json
{
  "timestamp":"2026-08-15T10:20:31.123Z",
  "level":"error",
  "service":"todo-api",
  "environment":"production",
  "trace_id":"7d3...",
  "span_id":"a91...",
  "route":"POST /todos",
  "error_type":"DependencyTimeout",
  "message":"database request exceeded deadline"
}
```

Never log access tokens, session cookies, passwords, full payment data, or unreviewed request bodies. Redact at the source and again in the pipeline where appropriate.

# 15.8.4 Failure lab

Generate 10,000 unique `request_id` labels and observe stream/cardinality impact in a disposable environment. Move the ID into parsed content, retain bounded labels, and compare query behavior. Then stop one collector and prove whether positions/checkpoints prevent unacceptable duplication or loss.

# 15.8.5 Production design

Use object storage, retention/compaction, replication, tenant isolation, ingestion/query limits, and query frontend/caching appropriate to scale. Test restore and object-store permissions. Monitor rejected samples, dropped lines, ingestion latency, chunk flushes, query performance, and storage errors.

# 15.8.6 Beginner mental model: a library of log streams

Imagine a warehouse that stores sealed boxes of paper. Loki does not build a giant word-by-word index for every page. It places a small label on each box—such as `cluster=prod`, `namespace=payments`, and `app=api`—and compresses the pages inside it. A query first finds the relevant boxes by their labels and then scans their contents.

That design explains both Loki's strength and its main rule:

```text
few stable labels + structured log body = efficient Loki
unique values as labels                = too many tiny streams
```

The smallest selectable unit is a **stream**: all entries with the same label set. A new label value can create a new stream. `environment=prod` has only a few possible values and is useful. `request_id=550e...` can have millions of values and is harmful as an indexed label.

# 15.8.7 The complete write and read paths

```text
WRITE
application stdout
  -> node log file
  -> collector discovers and checkpoints file
  -> labels/metadata added
  -> Loki distributor validates and shards
  -> ingester builds/compresses chunks
  -> object storage retains chunks and index

READ
Grafana/HTTP client
  -> query frontend splits and schedules query
  -> queriers locate matching streams
  -> relevant chunks fetched and filtered
  -> results merged and returned
```

This matters during an incident. A missing line may have failed at the application, container runtime, collector, gateway, distributor, ingester, storage, or query layer. “Loki lost it” is a hypothesis, not yet a diagnosis.

# 15.8.8 Intermediate LogQL: select, filter, parse, format

Build a query from cheap operations to expensive operations:

```logql
# 1. Narrow streams using indexed labels.
{cluster="prod", namespace="payments", app="checkout"}

# 2. Apply an exact line filter before parsing.
{cluster="prod", app="checkout"} |= "request_completed"

# 3. Parse JSON and test fields.
{cluster="prod", app="checkout"} |= "request_completed"
  | json
  | status_code >= 500
  | __error__=""

# 4. Produce a compact operator-friendly line.
{cluster="prod", app="checkout"} |= "request_completed"
  | json
  | status_code >= 500
  | line_format "{{.trace_id}} {{.method}} {{.route}} {{.duration_ms}}ms"
```

Other useful filters include `!=`, `|~` for a regular expression, and `!~` for a negative regular expression. Prefer exact filters where possible. A broad regex across every production stream is slower and makes accidental denial-of-service queries more likely.

# 15.8.9 Turning logs into temporary metrics

Metric queries answer aggregate questions without converting every log field into a permanent metric:

```logql
# Error lines per second, grouped by application.
sum by (app) (
  rate({cluster="prod", namespace="payments"} | json | level="error" [5m])
)

# Completed requests per status class.
sum by (status_class) (
  count_over_time(
    {app="checkout"} |= "request_completed"
      | json
      | __error__="" [5m]
  )
)

# P95 duration extracted from a numeric JSON field.
quantile_over_time(
  0.95,
  {app="checkout"} |= "request_completed"
    | json
    | unwrap duration_ms
    | __error__="" [5m]
)
```

Use native application metrics for durable SLOs and alerts. Log-derived metrics are excellent for investigation and low-volume events, but parsing cost and incomplete log delivery make them a weaker primary signal.

# 15.8.10 Label-design workshop

Classify each candidate before deployment:

| Candidate | Label? | Reason |
|---|---:|---|
| `cluster` | Yes | Small set and common query boundary |
| `namespace` | Yes | Bounded Kubernetes ownership boundary |
| `app` | Yes | Stable service selection |
| `environment` | Yes | Small, useful operational dimension |
| `level` | Usually no | Easily parsed; labels may fragment streams |
| `pod` | It depends | Helpful operationally, but churn must be understood |
| `route` | Usually parse | Route inventory can grow; validate bounds first |
| `trace_id` | No | Essentially unique per trace |
| `user_id` | No | High cardinality and sensitive |
| raw URL | No | IDs and query strings create unbounded values |

The word “bounded” is more important than “low today.” Ask what an attacker, tenant, new deployment strategy, or bug could make the value become tomorrow.

# 15.8.12 Query the lab and verify the data contract

In Grafana, add Loki as a data source with URL `http://loki:3100`. Open **Explore** and run:

```logql

```

1. Can you select the service without scanning unrelated streams?
2. Is `duration_ms` parsed as a number?
3. Does `__error__` remain empty?
4. Can the trace ID be displayed without being an indexed label?
5. Would any field expose a credential or personal identifier?

An observability lab is complete only when you can prove the signal answers a real operator question.

# 15.8.13 Break it: cardinality explosion

In a disposable instance, compare these models:

```text
Model A labels: app, environment
Model B labels: app, environment, request_id
```

Generate many unique request IDs, inspect Loki metrics such as active streams and ingestion behavior, and compare the query experience. Do not run this experiment against shared production. Remove the `request_id` label, keep it in JSON, restart the clean lab, and document the difference.

The remediation is a schema decision. Raising limits without fixing an unbounded label only postpones the failure.

# 15.8.14 Break it: timestamp and parsing failures

Test four malformed events:

```text
invalid JSON
timestamp far in the past
timestamp unexpectedly in the future
duration_ms written as "slow" instead of a number
```

Check collector rejected/dropped counters, Loki response codes, `__error__`, and the actual query time range. Preserve evidence before changing configuration. Permissive parsing that silently converts bad data can make dashboards convincingly wrong.

# 15.8.15 Professional investigation workflow

When an operator reports “logs are missing,” use an evidence ladder:

```text
1. Did the application write to stdout/stderr?
2. Is the line present in the node/container log file?
3. Did the collector discover the file and advance its checkpoint?
4. Did the exporter receive success, retry, reject, or drop?
5. Did Loki accept the tenant, labels, timestamp, and line size?
6. Are ingesters/object storage healthy?
7. Is the query using the correct tenant, labels, and time zone?
8. Did retention legitimately delete the data?
```

Record one timestamp, pod, node, and known line fragment. That creates a testable chain instead of random configuration changes.

# 15.8.16 Multi-tenancy, retention, and deletion

A production log platform needs policy, not only storage:

- Define tenant boundaries and enforce authentication outside or in front of Loki as required by the chosen architecture.
- Apply per-tenant ingestion, stream, query, and fairness limits.
- Use retention classes based on incident, legal, and privacy needs—not “keep everything.”
- Test object-store lifecycle rules against Loki retention/compaction behavior.
- Restrict deletion APIs and audit exceptional deletion workflows.
- Back up configuration and credentials; understand whether the object store is replicated or versioned.

Retention is a business control. Too short prevents investigations; too long increases cost, breach exposure, and compliance risk.

# 15.8.17 Security and privacy lab

Send a synthetic secret such as `demo_token=NEVER_USE_REAL_SECRET`, then prove your redaction stage replaces it before Loki. Search for both the original and redacted forms. The test passes only when:

```text
original secret is absent from stored/queryable logs
redacted marker is present
redaction failures have a metric and alert
configuration changes are reviewed and versioned
```

Never use a real key for this test. Also test encoded, differently cased, and nested JSON forms because simplistic patterns often miss them.

# 15.8.18 Capacity and reliability decisions

Estimate before scaling:

```text
daily raw bytes = peak/sustained log bytes per second × seconds per day
stored bytes    = raw bytes × compression factor × replication × retention days
query demand    = concurrent users × query range × selected stream volume
```

Measure real compression and query patterns instead of treating those variables as universal constants. Separate ingestion and query scaling, spread replicas across failure domains, test rolling upgrades, and alert on the platform's own RED signals. A logging system that cannot be observed becomes a second incident during the first one.

# 15.8.20 Interview preparation: beginner to expert

**Beginner: What is the difference between a label and a parsed field?**  A label is indexed and selects streams; a parsed field is extracted from log content during a query. Only bounded, frequently selected dimensions should normally become labels.

**Intermediate: Why should `trace_id` not be a Loki label?**  It is nearly unique, so it creates excessive streams/index cardinality. Keep it in structured content and search or pivot to it after narrowing by service and time.

**Intermediate: Why filter before `| json`?**  Label and exact line filters reduce the data that an expensive parser must process.

**Senior: Logs exist on the pod but not in Grafana. What do you check?**  Follow the write path: file discovery, permissions, checkpoints, parsing, exporter responses, Loki limits/tenant/timestamp, storage health, then query labels and time range.

**Expert: Would you alert from LogQL or Prometheus metrics?**  Prefer direct metrics for high-confidence service SLOs. Use log-derived metrics when the event naturally exists only in logs or during investigation, while accounting for delivery and parsing failure modes.

**Architect: How do you prevent one tenant from harming everyone?**  Authenticate tenant identity, apply per-tenant ingestion/query/stream limits and fairness, isolate sensitive data, observe usage, capacity-test, and provide controlled escalation rather than unlimited defaults.

**Never-forget answer:** Loki is efficient when labels describe a small set of streams and rich context stays in structured content. Query narrowly, observe the pipeline, and treat retention and redaction as production controls.

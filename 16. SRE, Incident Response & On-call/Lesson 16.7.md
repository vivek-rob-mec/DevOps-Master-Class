# Module 16 — SRE, Incident Response & On-call

## Lesson 7: Troubleshooting and Executable Runbooks

# 16.7.1 Scientific troubleshooting

```text
symptom and impact
→ scope and timeline
→ architecture/failure boundary
→ evidence
→ ranked hypotheses
→ discriminating test
→ reversible action
→ end-to-end validation
```

A hypothesis must predict evidence. “Kubernetes is broken” is not a useful hypothesis. “The new NetworkPolicy blocks API egress to PostgreSQL because denied connections began at the policy revision” is testable.

# 16.7.2 Work from outside inward

```text
client/DNS/CDN
→ load balancer/ingress
→ service/endpoints
→ pod/application
→ dependency/data
→ infrastructure/control plane
```

Choose the entry point based on evidence, but preserve the end-to-end model. Compare good vs bad region, instance, version, tenant, request type, and time window.

# 16.7.3 Runbook contract

Every paging runbook should contain:

```text
purpose and alert meaning
user impact and urgency
owner/escalation
safe access prerequisites
first diagnostics
decision tree
mitigation with scope and rollback
validation
evidence to retain
links and last-tested date
```

Commands use explicit placeholders and read-only checks first. Dangerous commands need approval and exact targeting.

# 16.7.4 Example decision tree

```text
high API error ratio
├── one version only? → halt rollout and restore stable traffic
├── one region only?  → inspect regional dependencies; consider traffic shift
├── all services?     → inspect shared DNS/identity/network/data
└── no real user impact? → verify SLI/query and telemetry integrity
```

# 16.7.5 Lab

Write and peer-test a runbook for `TodoApiHighErrorRatio`. Give it to someone who did not author it. They must diagnose a readiness failure and a dependency timeout without verbal hints. Record ambiguity, missing access, unsafe steps, and time to mitigation; revise the runbook.

# 16.7.6 Interview answer

> **I troubleshoot by defining impact, scope, and timeline, locating the failing boundary, and testing ranked hypotheses with discriminating evidence. I compare working and failing dimensions, prefer reversible authoritative fixes, and validate the user journey. Runbooks encode this decision process and are tested by responders who did not write them.**

# 16.7.7 Beginner mental model: doctor before medicine

A careful doctor asks symptoms, onset, scope, history, and performs discriminating tests before prescribing. Random medicine can hide evidence or create new harm. Production troubleshooting follows the same logic.

Start with what is observed, not a favorite cause:

```text
bad:  "database is broken"
good: "valid checkout writes in one region return 503 at 18%, starting 10:05 UTC"
```

# 16.7.8 Scope is a powerful diagnostic tool

Compare dimensions:

```text
good versus bad region
old versus new version
read versus write
one tenant versus all tenants
one route versus all routes
one dependency versus shared path
real traffic versus synthetic
before versus after a change
```

The smallest dimension that separates good from bad often identifies the failure boundary faster than reading thousands of logs.

# 16.7.9 Timeline and change correlation

Build a UTC timeline with:

```text
last known good
first bad user event
detection/page/declaration
deployments and config changes
traffic/capacity shifts
dependency/provider events
operator actions and observed results
```

Time correlation generates hypotheses; it does not prove cause. Confirm that the changed version or configuration appears in affected evidence and that reversal changes the symptom.

# 16.7.10 Rank hypotheses

For each hypothesis, write:

| Hypothesis | Predicted evidence | Cheap safe test | Risk |
|---|---|---|---|
| New app version fails writes | Errors isolated to version v42 | group SLI/log/trace by version | low |
| DB overloaded | pool wait and DB latency/saturation rise | inspect pool/DB signals | low |
| DNS issue | resolution failures by node/region | compare resolver evidence | low |

Test high-likelihood/high-impact hypotheses, but keep one path exploring common-mode catastrophic risks when evidence warrants it.

# 16.7.11 Evidence hierarchy

Prefer evidence closest to the user and authoritative system state:

```text
business outcome / user SLI
edge/server response and trace
application structured event
dependency behavior
resource/platform state
configuration/deployment record
human recollection
```

All can be useful. Treat logs and dashboards as measurements with collection/schema failure modes, not unquestionable truth.

# 16.7.12 Read-only checks first

Diagnostics should avoid mutation where possible:

```bash
kubectl get deployment,pod,service,endpointslice -n REPLACE_NAMESPACE
kubectl describe pod REPLACE_POD -n REPLACE_NAMESPACE
kubectl logs REPLACE_POD -n REPLACE_NAMESPACE --since=20m
kubectl logs REPLACE_POD -n REPLACE_NAMESPACE --previous
kubectl get events -n REPLACE_NAMESPACE --sort-by=.metadata.creationTimestamp
```

Use exact namespaces/names, trusted contexts, and approved access. Logs may contain sensitive data; collect the minimum necessary and preserve evidence securely.

# 16.7.13 Kubernetes failure boundaries

```text
Pod pending     -> requests, affinity/topology, quota, PVC, scheduler
CrashLoop       -> exit reason, previous log, config/secret, probe, OOM
Ready false     -> readiness behavior, dependency, port, startup
Service no path -> selectors, EndpointSlice, port mapping, policy
Ingress error   -> controller/backend/TLS/DNS/load balancer
Slow service    -> queue, CPU throttling, memory/GC, dependency, retry
```

Do not delete the pod before capturing status, events, previous termination, and configuration revision unless urgent mitigation requires it.

# 16.7.14 Runbook versus playbook

A runbook handles a specific known operational condition with executable decision paths. An incident playbook describes a broader process such as declaring SEV-1, communicating, or regional failover.

Both should state prerequisites, authorization, scope, and validation. Runbooks should help reasoning, not encourage blind command execution.

# 16.7.15 Production runbook template

```markdown
# Alert/condition name
Owner | Severity | Last tested | Required access

## Meaning and user impact
## Known false/no-data cases
## First five read-only checks
## Decision tree
## Mitigation A
- preconditions
- exact bounded action
- expected result/time
- abort/rollback
## Escalation and special risks
## Recovery validation using original SLI
## Evidence to preserve
## Links and change history
```

# 16.7.16 Real hands-on: executable runbook test

Create `TodoApiHighErrorRatio.md` and give it to a responder unfamiliar with the service. Secretly choose one fault:

```text
bad version serves only one zone
Service points to wrong target port
database timeout causes retry amplification
expired dependency certificate
SLI query missing one status label
```

The author may observe but cannot coach. Record first correct hypothesis, unsafe attempts, missing access, time to mitigation, recovery proof, and runbook ambiguity. Revise and repeat with another responder.

# 16.7.17 Add an evidence bundle

Automate safe collection of:

```text
service and deployment identity/version
pod status/events and resource state
selected component metrics/queries
recent rollout/config revisions
dependency health summary
exact UTC window and cluster/context
```

The collector must be read-only, bounded, redact secrets, and state incomplete/permission-denied results. An evidence bundle should reduce manual work without becoming a broad data-exfiltration tool.

# 16.7.18 Break it: misleading dashboard

Make the global error chart appear healthy by averaging a small failed region with a large healthy one. Ask the responder to find the hidden scope. Correct the dashboard with regional views and worst-scope visibility while keeping global customer weighting clear.

This trains the principle that aggregation can erase failure domains.

# 16.7.19 Break it: recovery command is unsafe

Place an ambiguous wildcard deletion example in a draft lab runbook and require peer review to reject it before execution. Replace it with read-only candidate enumeration, exact context/namespace/object, UID/precondition, batch limit, approval, and verification.

Never perform destructive testing against real user data or shared production.

# 16.7.20 Escalation triggers

Escalate when:

- data integrity, security, or safety may be involved;
- the runbook precondition is not met;
- impact grows or time threshold passes;
- required authority or domain knowledge is absent;
- two safe hypotheses are exhausted without progress;
- mitigation could affect another region/tenant or become irreversible;
- responder fatigue or cognitive overload becomes significant.

Escalation is a control, not failure.

# 16.7.21 Runbook lifecycle

Track owner, version, last tested, incident uses, feedback, dependencies, and deprecation. Test after architecture/access/tooling changes and during game days. A stale runbook can be more dangerous than no runbook because it creates false confidence.

# 16.7.22 Certification and interview preparation

Troubleshooting skill crosses Kubernetes, cloud, observability, and SRE certification scenarios. Current product commands matter, but evidence-driven reasoning is durable.

**Beginner: What is the first troubleshooting step?**  Define exact user impact, scope, time, and last known good before assuming a cause.

**Intermediate: What is a discriminating test?**  A safe check whose result meaningfully separates competing hypotheses.

**Intermediate: Why compare good and bad dimensions?**  The boundary where behavior diverges narrows version, region, tenant, route, or dependency causes.

**Senior: What makes a runbook executable?**  Meaning, prerequisites, first evidence, decision branches, bounded actions, expected results, abort/rollback, escalation, and end-to-end validation—all tested by another responder.

**Senior: Why read-only first?**  It preserves evidence and reduces the chance that diagnosis creates a second incident.

**Expert: Metrics and logs disagree—what do you trust?**  Examine each signal's measurement boundary, coverage, time, schema, sampling, and collection health; use authoritative user/business outcomes and independent evidence.

**Architect: How do you scale troubleshooting knowledge?**  Standard telemetry/ownership, service maps, tested runbooks, safe evidence automation, game days, postmortem learning, and tools that expose failure boundaries without hiding reasoning.

**Never-forget answer:** state the symptom, narrow scope, make hypotheses predict evidence, test safely, and validate recovery from the user's point of view.

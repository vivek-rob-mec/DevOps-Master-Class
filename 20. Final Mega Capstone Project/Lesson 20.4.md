# Module 20 — Final Mega Capstone Project

## Lesson 4: Terraform, EKS and Cluster Bootstrap

# 20.4.1 Terraform ownership

Terraform creates:

```text
VPC/endpoints and security boundaries
EKS control plane and node capacity
IAM roles and EKS access entries
KMS/storage/database primitives
registry and bootstrap identities
initial version-pinned Argo CD installation or handoff
```

Argo owns declarative in-cluster platform add-ons and workloads after the documented boundary. One resource field has one authority.

# 20.4.2 EKS baseline

```text
private API access or controlled network path
multi-AZ nodes and multiple capacity types
workload identity
envelope encryption where required
control-plane logging
managed add-ons with pinned compatibility
autoscaling and interruption handling
backup/recovery integration
```

Separate system/platform nodes from tenant capacity when blast radius or scheduling needs justify it.

# 20.4.3 Bootstrap order

```text
cluster and access
→ CNI/DNS/storage prerequisites
→ Argo CD management control plane
→ foundation AppProject/ApplicationSet
→ policy, ingress, certificates, secrets, observability
→ workload projects and applications
```

Do not rely on sync waves across unrelated Applications as a full readiness orchestrator. Foundation and workload Applications should have explicit health gates and documented dependency behavior.

# 20.4.4 Workload baseline

Enforce namespaces, RBAC, quotas, network policies, approved registries, non-root/least privilege, resource requests, health probes, topology, PDB, immutable images, owner/cost labels, and telemetry.

# 20.4.5 Upgrade plan

Track Kubernetes, EKS platform, AMI/runtime, add-ons, Argo, policy, ingress, secrets, observability, and workload APIs. Test version skew and deprecated APIs. Canary non-production, then platform, then workloads by tier. Define rollback boundaries because cluster version downgrade may not exist.

# 20.4.6 Acceptance tests

```text
□ authorized access works; unauthorized access fails
□ node/zone loss preserves critical journey
□ unschedulable load provisions bounded capacity
□ tenant isolation negative tests pass
□ platform bootstrap works from clean cluster
□ API/add-on upgrade rehearsal succeeds
□ cleanup targets only capstone resources
```

# 20.4.7 Terraform ownership graph

```text
foundation state: accounts, remote state, audit
network state: VPC/subnets/routes/endpoints
cluster state: EKS control plane/node classes/identity integrations
bootstrap state: minimal GitOps prerequisites
GitOps: add-ons, tenant baseline, applications
```

Avoid Terraform and Argo CD both owning the same Kubernetes object. Document import/migration boundaries.

# 20.4.8 Terraform production workflow

```text
format/validate -> lint/security/policy -> plan
-> reviewed saved plan and cost/risk summary
-> apply with scoped identity/lock
-> smoke/security/telemetry validation
-> state/actual reconciliation
```

Pin providers/modules, constrain versions, and test upgrades. Keep state encrypted, versioned, locked, backed up, and access-audited.

# 20.4.9 EKS architecture

Decide:

```text
cluster per environment/trust class
Kubernetes/control-plane version and support window
public/private API endpoint and admin access
subnet/AZ/IP design
managed/self-managed/serverless node options
node classes, autoscaling, Spot eligibility
pod/service networking and network policy
storage/CSI classes
identity/access and secrets integration
logging/telemetry
upgrade and DR
```

Use current EKS best practices and supported add-on/version matrices.

# 20.4.10 Node and workload capacity

Model normal, rollout, one-node, and one-zone demand. Include DaemonSets, system pods, IPs, volumes, PDB/topology, startup/image pull, HPA/node-provisioning lag, and dependency quotas.

Create a protected system node class where justified and diversified workload classes without excessive fragmentation.

# 20.4.11 Bootstrap boundary

Terraform should install only what is necessary to establish GitOps safely, then Argo CD reconciles declared platform layers:

```text
0 cluster/network/identity
1 Argo CD prerequisites/control plane
2 repositories/projects/clusters and secret references
3 CNI/CSI/DNS/ingress/cert/policy as ownership dictates
4 observability/secrets/operators
5 tenant baseline
6 applications
```

Exact ownership/order depends on add-on lifecycle and cluster prerequisites.

# 20.4.12 Add-on governance

Inventory CNI, DNS, proxy, CSI, ingress, autoscaler/provisioner, metrics, policy, secrets, GitOps, observability, and security agents with owner, source, version, compatibility, configuration, SLO, upgrade, and rollback.

Privileged node agents/operators receive heightened supply-chain/RBAC review.

# 20.4.13 Workload baseline

Require:

```text
owner/service/version/environment labels
requests and tested limits
startup/readiness/liveness semantics
non-root/no privilege escalation/security profile
dedicated ServiceAccount/workload identity
NetworkPolicy and egress contract
topology/spread and disruption policy by SLO
graceful shutdown and termination budget
telemetry/SLO/runbook/cost allocation
```

# 20.4.14 Real hands-on cluster plan

Create reviewed Terraform for a small lab EKS cluster or a no-cost plan if cloud creation is unavailable. Required outputs expose safe identifiers—not secret kubeconfig tokens. Run:

```bash
terraform fmt -check -recursive
terraform init -backend=false
terraform validate
terraform plan -out=REPLACE_SAFE_PLAN_PATH
terraform show REPLACE_SAFE_PLAN_PATH
```

Use the real remote backend only in approved accounts with locking and scoped credentials.

# 20.4.15 Real hands-on bootstrap

Install/version-pin Argo CD through the chosen bootstrap owner. Commit AppProjects, repository/cluster secret references, root applications/ApplicationSets, platform add-ons, tenant baseline, and Atlas applications in separate layers.

Verify a cluster can be rebuilt from Terraform + Git + approved secret/backup systems.

# 20.4.16 Security tests

Attempt:

```text
unauthorized Kubernetes admin access
workload uses node role or another ServiceAccount identity
privileged/hostPath pod
cross-namespace secret/network access
untrusted image or unsigned artifact under project policy
public API endpoint from unapproved network
Terraform identity mutates unrelated account resources
```

# 20.4.17 Reliability tests

```text
delete one application pod -> self-heals and SLI remains
drain one node -> PDB/topology/capacity behavior
simulate one-zone capacity loss -> scheduling and SLO
break one add-on -> clear detection and controlled recovery
restart GitOps controller -> running apps continue/reconciliation resumes
fill pod/IP quota safely -> alert/runbook/load controls
```

# 20.4.18 Upgrade rehearsal

Inventory deprecated APIs and compatibility. Upgrade in nonproduction/canary cluster or node class, then control plane/add-ons/nodes/workloads in supported order. Test PDB/topology/capacity, DNS/network/storage, telemetry, GitOps, admission, and rollback limits.

A control-plane version downgrade may not be supported; rollback often means restore/forward remediation. Verify current EKS documentation.

# 20.4.19 Disaster recovery

Separate cluster reconstruction from application data recovery. Back up Git/IaC state, Argo CD required state if not fully reconstructable, cluster-scoped/namespaced resources as policy, secrets/keys through approved systems, and persistent data through its owner.

Restore into isolation and validate user journeys/identity/policy/telemetry.

# 20.4.20 Acceptance checklist

- Terraform state boundaries/owners and GitOps boundary are clear.
- Cluster/node/network/IP capacity covers failure/rollout.
- Identity/RBAC/workload/tenant controls pass denial tests.
- Add-ons are versioned, owned, observable, upgrade-tested.
- Workload baseline passes policy and failure tests.
- Running workloads survive GitOps/portal loss as designed.
- Node/zone/upgrade tests meet SLO.
- Cluster and data recovery are separately proven.
- Cost/budget/teardown inventory is complete.

# 20.4.21 Certification and interview preparation

This lesson bridges Terraform, Kubernetes/CKA-style concepts, EKS, GitOps, security, and reliability. Verify current exam/provider objectives.

**Beginner: Terraform versus Argo CD ownership?**  Terraform typically owns cloud/cluster foundations; Argo CD continuously owns declared Kubernetes/platform/application resources. Never dual-own silently.

**Intermediate: Why requests matter?**  Scheduler and node capacity use requests; incorrect values cause waste or contention/failed scheduling.

**Intermediate: What does PDB guarantee?**  It constrains supported voluntary disruptions; it does not guarantee capacity or prevent all failure/deletion.

**Senior: How bootstrap GitOps without circularity?**  Terraform or a minimal controlled process creates cluster and required Argo prerequisites; Argo then owns layered desired state with documented recovery.

**Senior: How do you upgrade EKS safely?**  Compatibility/API inventory, canary/nonprod, capacity/disruption tests, supported control/add-on/node sequence, workload validation, and recovery/forward plan.

**Expert: How prove multi-AZ?**  Placement plus actual zone-equivalent loss at peak/rollout, covering nodes/IP/storage/network/data/dependencies and user SLI.

**Architect: What rebuilds a lost cluster?**  Versioned Terraform, GitOps intent, artifact registry, identity/keys/secrets recovery, application data restore, external DNS/config, and tested runbook.

**Never-forget answer:** own each layer once, bootstrap minimally, version the entire cluster platform, and test node/zone/upgrade/rebuild from the user journey.

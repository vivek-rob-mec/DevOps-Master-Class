# Module 15 — Observability

## Lesson 12: Application Instrumentation

# 15.12.1 Instrument the boundary

Start at ingress, dependency calls, queues, database access, and business outcomes. Standard HTTP/database/client instrumentation gives a baseline; manual spans and metrics describe domain-specific work.

```text
request received
→ trace server span
→ request counter and duration histogram
→ structured completion/error log with trace_id
→ child spans for dependencies
→ business counter only after authoritative outcome
```

# 15.12.2 Metric contract

```text
http_server_requests_total{service,route,method,status_class}
http_server_request_duration_seconds_bucket{service,route,method,le}
todo_created_total{service,result}
dependency_requests_total{service,dependency,result}
```

Do not label with request ID, user ID, raw exception, or raw URL. Predeclare allowed route and outcome values. Count retries separately so apparent traffic does not hide dependency instability.

# 15.12.3 Trace contract

Use semantic conventions where available. Record stable operation name, service resource, route, method, response status, dependency system, and error status. Do not make every function a span. Spans should represent meaningful boundaries and latency.

For asynchronous work:

```text
producer span → inject context into message headers
consumer span → extract context and link/parent appropriately
record queue time separately from processing time
```

# 15.12.4 Logging contract

Log one structured completion event rather than many vague messages. Include timestamp, severity, service, environment, event name, trace/span ID, route, result, duration, and safe error classification. Keep human text plus machine-queryable fields.

# 15.12.5 Lab

Instrument one Python or Node service with OpenTelemetry auto-instrumentation, then add one manual business counter and span. Test success, validation failure, dependency timeout, retry, and cancellation. Verify:

```text
metrics do not double count
trace context crosses service boundary
errors set correct span status
logs carry trace_id
shutdown flushes telemetry
cardinality remains bounded
```

# 15.12.6 Interview answer

> **I instrument stable service boundaries first, use semantic conventions, expose RED metrics, propagate trace context, and emit structured completion/error logs containing trace IDs. Manual instrumentation describes business outcomes and important internal work. I test retries, async context, shutdown flush, PII controls, and cardinality just like application behavior.**

# 15.12.7 Beginner mental model: dashboard instruments for software

A driver does not open the engine every minute. Speed, temperature, fuel, and warning lights expose selected facts about the vehicle. Application instrumentation does the same for software.

Good instrumentation begins with questions:

```text
Are users succeeding?
How long do requests take?
Which dependency is slow or failing?
How much work is waiting?
Did a business operation actually complete?
```

Adding every possible field is not observability. It creates cost, cardinality, privacy risk, and noise. Instrument the decisions operators need to make.

# 15.12.8 Automatic and manual instrumentation

Automatic instrumentation can create standard spans and metrics around supported frameworks and libraries without editing every call site. Manual instrumentation adds application-specific meaning.

| Type | Strength | Limitation |
|---|---|---|
| Automatic | Fast coverage of HTTP, DB, RPC, messaging | Cannot fully understand business outcomes |
| Library instrumentation | Consistent reusable telemetry | Must remain application-neutral |
| Manual | Domain operations and custom attributes | Easy to over-instrument or become inconsistent |

Use automatic instrumentation to establish the roads, then manual instrumentation to mark the important destinations.

# 15.12.9 A telemetry contract before code

For every endpoint or worker, define:

```text
operation name: stable route or job name
success: exact authoritative condition
failure classes: validation, dependency, internal, cancellation
latency boundary: where timing starts and stops
metric labels: bounded allowed values
trace attributes: searchable and safe
log fields: structured completion context
owner: team responsible for correctness
```

For `POST /todos`, a `202` response might mean “accepted to a queue,” not “todo persisted.” Emit separate accepted, processing, and completed business outcomes. Otherwise a green HTTP dashboard can hide failed asynchronous work.

# 15.12.10 RED, USE, and business signals

Instrument service boundaries with RED:

```text
Rate     requests or jobs per second
Errors   failed outcomes per second/ratio
Duration latency distribution
```

Instrument constrained resources with USE:

```text
Utilization  how busy the resource is
Saturation   queued work/throttling
Errors       failed operations
```

Add carefully chosen business signals such as `orders_completed_total{result}`. Business metrics must be emitted only after the authoritative outcome and must have an owner. Never derive revenue from retry attempts.

# 15.12.11 Choosing metric instruments

```text
monotonic event count         -> counter
current queue depth           -> observable/up-down gauge as supported
request duration distribution -> histogram
current in-flight requests    -> up-down counter or gauge pattern
```

Choose histogram boundaries based on user and SLO thresholds. If the important latency target is 300 ms but the nearest useful buckets are 250 ms and 500 ms, the query cannot precisely estimate compliance at 300 ms. Native or exponential histograms may be available in a chosen stack, but verify end-to-end support and operational tradeoffs.

# 15.12.12 Cardinality budget

Estimate a metric's possible series before release:

```text
series ≈ routes × methods × status classes × instances × environments
```

For 25 routes, 4 methods, 5 status classes, 40 instances, and 3 environments:

```text
25 × 4 × 5 × 40 × 3 = 60,000 possible series
```

Not every combination occurs, but the estimate exposes risk. Replace raw paths with route templates, group status codes where appropriate, remove redundant dimensions, and place request-level IDs in logs/traces.

# 15.12.13 Real hands-on: manual Python instrumentation

The following focuses on instrumentation logic. Pin mutually compatible package versions in a virtual environment and use current package documentation for setup.

```python
import time
from flask import Flask, jsonify, request
from opentelemetry import metrics, trace
from opentelemetry.trace import Status, StatusCode

app = Flask(__name__)
tracer = trace.get_tracer("training.todo-api")
meter = metrics.get_meter("training.todo-api")

created = meter.create_counter(
    "todo.created",
    unit="{todo}",
    description="Authoritatively created todos",
)
duration = meter.create_histogram(
    "todo.create.duration",
    unit="s",
    description="Todo creation operation duration",
)

@app.post("/todos")
def create_todo():
    started = time.perf_counter()
    result = "success"

    with tracer.start_as_current_span("create_todo") as span:
        span.set_attribute("app.operation", "create_todo")
        try:
            title = (request.get_json(silent=True) or {}).get("title", "").strip()
            if not title:
                result = "validation_error"
                span.set_attribute("app.result", result)
                return jsonify(error="title is required"), 400

            # A real implementation persists before counting success.
            todo = {"id": "synthetic-001", "title": title}
            created.add(1, {"app.result": "success"})
            span.set_attribute("app.result", "success")
            return jsonify(todo), 201
        except TimeoutError as exc:
            result = "dependency_timeout"
            span.record_exception(exc)
            span.set_status(Status(StatusCode.ERROR, "dependency timeout"))
            return jsonify(error="temporarily unavailable"), 503
        finally:
            duration.record(
                time.perf_counter() - started,
                {"app.result": result},
            )
```

This code intentionally does not attach title, user ID, todo ID, or exception text as metric attributes. The ID belongs in safe logs/traces only when operationally justified.

# 15.12.14 Configure providers and export

Creating instruments is not enough. The application must configure an SDK provider, resource, reader/processor, exporter, and shutdown path. Environment-driven OTLP configuration is useful across languages:

```bash
export OTEL_SERVICE_NAME=todo-api
export OTEL_RESOURCE_ATTRIBUTES="service.version=lab-1,deployment.environment.name=lab"
export OTEL_EXPORTER_OTLP_ENDPOINT="http://localhost:4318"
export OTEL_EXPORTER_OTLP_PROTOCOL="http/protobuf"
```

Exact environment variables and exporter packages depend on language and version. Validate receiver protocol and path. OTLP/HTTP and OTLP/gRPC are not interchangeable merely because both are OTLP.

# 15.12.15 Structured logs with trace correlation

At operation completion, log an event resembling:

```json
{
  "timestamp": "2026-08-15T10:20:31.123Z",
  "severity": "INFO",
  "service": "todo-api",
  "event": "todo_create_completed",
  "route": "POST /todos",
  "result": "success",
  "duration_ms": 42,
  "trace_id": "current-trace-id",
  "span_id": "current-span-id"
}
```

Extract IDs from the current valid span context using the language SDK. Do not generate unrelated IDs or copy a stale thread-local value. Logging libraries and OpenTelemetry integrations may inject correlation fields automatically; test async behavior and formatting.

# 15.12.16 Propagate across an HTTP dependency

Use an instrumented HTTP client so the current context is injected. On the server, framework instrumentation should extract it and create a server span. Verify:

```text
client and server share one trace ID
server parent points to the client span
outbound timeout is set
retry attempts are visible without double-counting business success
dependency name is stable and safe
```

If an intermediary strips tracing headers, fix its explicit forwarding policy. Do not smuggle context in query strings.

# 15.12.17 Propagate through a queue

For an asynchronous job:

```text
API accepts request
  -> producer span injects context into approved message metadata
  -> queue time passes
  -> consumer extracts context
  -> consumer span processes job
  -> authoritative completion counter increments once
```

Test duplicate delivery, retry, dead-letter routing, and delayed consumption. An idempotency strategy belongs to business processing; telemetry should expose attempts and final outcomes separately.

# 15.12.18 Test instrumentation like application code

Write automated checks for:

- exact metric name, unit, type, and allowed attribute keys;
- success counted once after persistence;
- validation failure does not increment success;
- retry increments attempt data but not business completion twice;
- span name is the route template, never a raw ID path;
- status/error behavior matches current semantic conventions;
- trace IDs appear in correlated logs;
- synthetic secret fields are absent;
- shutdown flush completes within the termination budget.

Use in-memory/test exporters where supported. Assertions make telemetry contract drift visible during CI.

# 15.12.19 Break it: double registration and duplicate counting

Create two common bugs deliberately:

1. Add both automatic and manual HTTP request metrics with the same intent.
2. Increment `todo_created` before a dependency succeeds, then retry.

Observe conflicting names, duplicate series, or inflated business results. Remediate by assigning one authoritative instrument per outcome and documenting ownership between auto-instrumentation and application code.

# 15.12.20 Break it: context loss and exporter outage

Move work into an uninstrumented thread/task and inspect whether the child retains its parent. Then block OTLP export while sending requests. Check:

```text
SDK queue size/limits where observable
application latency impact
retry and drop behavior
memory pressure
recovery and shutdown flush
```

Telemetry must not create an unlimited failure cascade. Use bounded asynchronous export, explicit timeout/retry policy, and a documented data-loss boundary.

# 15.12.21 Security and performance review

Before release, review:

```text
labels/attributes for cardinality
headers, query strings, SQL, exceptions, and payloads for sensitive data
baggage for trust and privacy
instrumentation CPU/allocation overhead
export queue memory and network cost
sampling and retention assumptions
who can change configuration
```

Measure with and without instrumentation under representative load. “Low overhead” is a claim that must be tested for this application, traffic, language runtime, and exporter configuration.

# 15.12.23 Interview preparation: beginner to expert

**Beginner: What is instrumentation?**  Code or configuration that records measurements and context so operators can understand software behavior.

**Beginner: Auto versus manual instrumentation?**  Auto-instrumentation covers supported technical libraries quickly; manual instrumentation adds business operations and organization-specific meaning.

**Intermediate: Why use a histogram for latency?**  It preserves a distribution that supports percentiles and threshold/SLO analysis across aggregated traffic; an average hides the tail.

**Intermediate: Why not label metrics with user ID?**  It creates unbounded series, high cost, slow queries, and privacy risk. Use bounded aggregate dimensions and safe trace/log context when necessary.

**Senior: When should a success counter increment?**  Only after the authoritative outcome. Accepted, attempted, retried, and completed are separate events.

**Senior: How do you prevent auto and manual instrumentation from duplicating data?**  Inventory instrument ownership, disable overlapping instrumentation or give the custom metric a distinct business meaning, then test counts.

**Expert: Telemetry export is down. Should requests fail?**  Normally telemetry uses bounded asynchronous delivery and should not take the service down; the exact loss/durability policy depends on business requirements. Monitor and test the failure boundary.

**Architect: How do you govern telemetry across hundreds of services?**  Publish versioned resource and signal contracts, standard libraries/templates, cardinality and privacy gates, CI tests, backend usage monitoring, ownership, and a reviewed exception process.

**Never-forget answer:** instrument meaningful boundaries and authoritative outcomes. Use stable names, bounded attributes, safe correlation, and test telemetry under retry, failure, async, and shutdown conditions.

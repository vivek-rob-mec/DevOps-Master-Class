# Module 15 — Observability

## Lesson 13: Correlating Metrics, Logs and Traces

Correlation turns three separate tools into one investigation system.

# 15.13.1 Shared context

Use consistent values for:

```text
service.name
service.namespace
deployment.environment.name
k8s.cluster.name
k8s.namespace.name
cloud.region
service.version
```

Metrics aggregate populations, so do not add trace IDs as ordinary metric labels. Use exemplars to attach selected trace IDs to histogram observations. Logs can safely store trace IDs as fields because they are queried as content rather than indexed stream labels.

# 15.13.2 Investigation workflow

```text
SLO burn alert
→ service dashboard identifies latency window and route
→ histogram exemplar opens slow trace
→ trace shows payment dependency span
→ trace_id opens correlated logs
→ deployment annotation identifies new version
→ rollback/fix authoritative source
→ validate SLI recovery
```

If any arrow fails, the observability experience is incomplete.

# 15.13.3 Grafana data links

Configure:

```text
Prometheus exemplar → Tempo trace
Loki derived field trace_id → Tempo trace
Tempo span → Loki logs using service/time/trace
Tempo metrics generator → service graph/span metrics
dashboard annotation → deployment/Git revision
```

Keep links portable by using variables and consistent attributes rather than hard-coded namespaces.

# 15.13.4 Lab — one-click investigation

Generate a slow failing request. Start only from the page alert. Capture evidence that you can reach:

1. The affected service and route.
2. A representative trace.
3. The failing span.
4. Matching structured logs.
5. The deployed version and Git revision.
6. The runbook and owner.

Repeat after renaming a service label incorrectly. Repair enrichment at the source or Collector so all signals converge on one resource identity.

# 15.13.5 Production checklist

```text
□ Common resource schema is versioned
□ Trace context crosses HTTP, gRPC, and messaging
□ Logs contain trace/span identifiers
□ Histograms carry exemplars where supported
□ Deployments are annotated
□ Cross-data-source links are tested
□ Sensitive attributes are removed before storage
```

# 15.13.6 Beginner mental model: three camera views of one event

Suppose a stadium has a crowd counter, security reports, and video footage:

```text
metric -> 2% of entrances are failing
log    -> gate 7 reports scanner timeout with context
trace  -> one visitor's request waited on identity service
```

No signal replaces the others. Correlation means they use enough shared, safe identity and time context that a responder can move between them without guessing.

# 15.13.7 Identity hierarchy

Standardize resource identity at the organization level:

```text
organization
  -> cloud account/subscription
  -> region
  -> cluster
  -> namespace
  -> service namespace
  -> service name
  -> service version/instance
```

Not every level belongs on every metric. Keep Prometheus label sets bounded. Logs and traces may carry richer context, subject to privacy and cost controls. The important requirement is semantic agreement: `todo-api` cannot be `todo_service` in metrics, `todos` in logs, and `backend` in traces if automated pivots depend on the value.

# 15.13.8 Time is part of correlation

Signals can share an ID and still appear unrelated when clocks or time ranges differ. Control:

- node and application time synchronization;
- UTC timestamps at the source;
- event time versus ingestion time;
- Grafana browser time zone and selected range;
- queue delays and late-arriving telemetry;
- trace search windows around a log event.

During an incident, write the relevant window in UTC and widen it by known pipeline delay. A “missing” event is often outside the selected time range.

# 15.13.9 Exemplars without cardinality explosion

An exemplar attaches selected trace context to an individual metric observation, often a histogram sample. It does not turn the trace ID into a permanent label on every time series.

```text
latency histogram bucket/time point
  └── exemplar {trace_id="..."}
        └── open exact trace in Tempo
```

Exemplar availability depends on the instrumentation library, sampling, Prometheus storage/configuration, query path, and Grafana data-source setup. Test the entire route. Absence of an exemplar does not mean the metric is wrong; it means this pivot is unavailable for that observation.

# 15.13.10 Logs-to-traces and traces-to-logs

For logs to traces, parse a valid trace ID field and configure a derived/data link to the Tempo data source. For traces to logs, construct a Loki query from trusted resource attributes and a narrow time window:

```logql
{cluster="prod", namespace="payments", app="checkout"}
  | json
  | trace_id="${__trace.traceId}"
```

Treat this as a template concept; Grafana variable syntax and data-link configuration must match the installed version. Keep trace IDs in log content, not Loki labels.

# 15.13.11 Release correlation

A deployment marker should contain immutable facts:

```json
{
  "service": "checkout-api",
  "environment": "production",
  "service_version": "2026.08.15.3",
  "image_digest": "sha256:example",
  "config_revision": "git-example",
  "rollout_started_at": "2026-08-15T12:00:00Z",
  "rollout_result": "healthy"
}
```

Grafana annotations are a convenient view, but Git, deployment controllers, or an event store should retain the authoritative audit record. Correlate on version and time; do not add every commit SHA to long-lived metric labels.

# 15.13.12 Real hands-on: build the golden path

Use the instrumented service from Lesson 15.12 and complete these steps:

1. Expose a request-duration histogram with exemplars if the client library supports them.
2. Send structured completion logs containing the current trace/span ID.
3. Export traces to Tempo and logs to Loki.
4. Configure Prometheus, Loki, and Tempo data sources in Grafana.
5. Add a Prometheus-to-Tempo exemplar link.
6. Add a Loki trace-ID link.
7. Add a Tempo-to-Loki query using service identity and trace ID.
8. Add a deployment annotation for the service version.

Generate one slow 500 response and save screenshots or an investigation recording showing every pivot.

# 15.13.13 Prove semantics at every pivot

The final trace must not merely have the same timestamp. Verify:

```text
metric route/result describes the failing population
exemplar trace belongs to that metric observation
trace resource identifies the same service/environment/version
failing span identifies a causal dependency
log trace_id exactly matches the trace
log event explains the safe error classification
deployment marker covers the version and time
```

Correlation is evidence linking facts, not a visual coincidence.

# 15.13.14 Break it: identity drift

Change `service.name` only in the Collector, or alter `app` only in Loki labels. Observe which links fail while data continues to arrive. Repair the authoritative enrichment rule and add a contract test that compares the approved service inventory with recent resources/labels.

Avoid dashboard-by-dashboard repair. Hard-coding aliases in every query turns one schema defect into permanent configuration debt.

# 15.13.15 Break it: sampled trace and absent exemplar

Run low-rate head sampling and generate a slow metric observation whose trace is not retained. Document the operator experience:

```text
metric still proves population impact
exemplar may be absent
logs can still narrow by service/route/time
other sampled traces may explain the pattern
sampling policy is visible to responder
```

Design an investigation path that works even when no exact trace was sampled.

# 15.13.16 Break it: delayed logs and clock skew

Delay log export and skew a disposable workload clock within a safe lab. Watch the trace-to-log default window miss the event. Correct time synchronization, restore the pipeline, and choose a link window that accounts for normal delay without scanning hours of unrelated logs.

# 15.13.17 Professional incident workflow

Start with population evidence and progressively increase detail:

```text
1. Confirm user-facing SLI and scope.
2. Compare routes, regions, clusters, and versions.
3. Mark the exact bad interval and recent changes.
4. Select a representative exemplar or trace.
5. Identify the critical path and failing dependency.
6. Inspect correlated logs using trace/time/service filters.
7. Mitigate through the authoritative system.
8. Re-check the original SLI, not only component health.
```

One trace cannot prove population-wide impact, and one log line cannot establish a rate. Return to metrics to validate scope and recovery.

# 15.13.18 Security and tenancy

A cross-signal link must not become an access-control bypass. Ensure that:

- Grafana data-source permissions match tenant/team authorization;
- a user allowed to see a metric cannot automatically access restricted logs;
- links do not place sensitive IDs in URLs or browser history unnecessarily;
- tenant identity is derived from authenticated context;
- dashboards and query history do not leak secrets;
- audit logs cover access to sensitive telemetry.

Correlation increases investigative power and therefore increases the need for consistent authorization.

# 15.13.19 Production schema contract

Maintain a versioned table with, at minimum:

| Concept | Metric | Log | Trace | Source/owner |
|---|---|---|---|---|
| Service | `service` label | `service` field/label | `service.name` resource | platform contract |
| Environment | bounded label | structured field/label | deployment environment resource | deployment platform |
| Version | dashboard info/join or event | field | resource attribute | build/deployment |
| Route | normalized label | field | semantic span attribute | HTTP instrumentation |
| Trace ID | exemplar only | content field | native context | tracing SDK |

Include allowed values, sensitivity, cardinality expectation, and deprecation policy.

# 15.13.20 Certification and interview preparation

This lesson combines core observability concepts, resource identity, trace/log correlation, exemplars, dashboards, and troubleshooting. Check the current Prometheus and OpenTelemetry certification objectives for exact scope.

**Beginner: Why use all three signals?**  Metrics show population behavior, traces show one request's causal path, and logs provide discrete contextual events.

**Intermediate: Why not attach trace ID as a metric label?**  It creates nearly one time series per request. Exemplars associate selected observations without expanding the base label set that way.

**Intermediate: What makes a trace-to-log link reliable?**  Consistent resource identity, valid trace IDs in structured logs, synchronized time, correct tenant/access, and a tested query template.

**Senior: An alert has no exemplar. Can you investigate?**  Yes. Scope with metric dimensions and time, use service/version logs, search sampled traces for the affected operation, and account for the sampling policy.

**Expert: All signals arrive, but links fail after a rename. Where do you fix it?**  At the authoritative telemetry schema/enrichment source, followed by contract tests and controlled migration—not with permanent aliases in every dashboard.

**Architect: What is the security risk of correlation?**  It joins data domains. Enforce authorization per destination, trusted tenant identity, safe URL/link handling, privacy controls, and auditability.

**Never-forget answer:** correlation needs shared identity, context, and time. Start with aggregate impact, pivot to causal detail, and return to the SLI to prove recovery.
